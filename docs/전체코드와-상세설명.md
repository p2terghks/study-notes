# 전체 코드와 상세 설명

[← 단계별 학습 안내로 돌아가기](처음부터-웹-만들기.md)

이 문서는 프로젝트의 실제 코드와 같은 순서로 읽을 수 있습니다. 완성 코드는 이미 파일에 작성되어 있으므로 실행하면서 한 파일씩 살펴보세요. 직접 다시 작성하고 싶다면 별도 폴더에서 아래 순서를 따라 하세요.

## 1. 웹은 어떻게 움직일까요?

브라우저는 화면을 보여주고 사용자의 입력을 받습니다. 서버는 요청을 받아 처리하고 응답합니다. DB는 데이터를 저장합니다.

예를 들어 `할 일 저장` 버튼을 누르면 다음 일이 일어납니다.

```text
브라우저: title=스프링 공부를 POST /todos로 보냄
   ↓
Controller: 입력을 TodoForm에 담고 검증
   ↓
Service: 새 할 일을 저장하는 작업 수행
   ↓
Repository: save(todo) 호출
   ↓
JPA 구현체(Hibernate): INSERT SQL 생성 및 JDBC로 전달
   ↓
H2 DB: 데이터 저장
   ↓
서버: /todos로 이동하라는 응답
   ↓
브라우저: GET /todos 요청 → 목록 HTML 표시
```

HTTP는 브라우저와 서버의 요청·응답 규칙입니다. URL은 요청할 주소입니다. HTML은 화면의 구조, CSS는 모양을 표현합니다. 이 예제는 서버가 HTML을 완성해 보내므로 JavaScript 없이도 작동합니다.

## 2. 웹에는 어떤 기능이 필요할까요?

모든 웹이 같은 기능을 요구하지는 않습니다. 게시판, 쇼핑몰, 일정 관리에서는 다음 기능을 자주 씁니다.

| 필요한 기능 | 할 일 예제에서의 모습 | 담당 코드 |
|---|---|---|
| 화면 표시 | 목록·등록·수정 화면 | HTML + Thymeleaf |
| 요청 처리 | 주소와 실행 메서드 연결 | Controller |
| 작업 규칙 | 신규 등록은 미완료 상태로 시작 | Service + Entity |
| 저장·조회 | 서버 재시작 후에도 할 일 유지 | Repository + JPA + DB |
| 입력 검증 | 공백 거부, 100자 제한 | TodoForm + @Valid |
| 오류 처리 | 없는 할 일은 404 | 예외 클래스 + 오류 화면 |
| 동작 확인 | 저장부터 삭제까지 검증 | 통합 테스트 |
| 로그인·권한 | 나의 할 일만 변경 | 다음 학습 단계 |

등록(Create), 조회(Read), 수정(Update), 삭제(Delete)를 묶어 **CRUD**라고 합니다. 이번 예제는 이 네 기능을 모두 구현합니다.

## 3. 먼저 알아둘 Java 문법

- `class`: 객체의 설계도입니다. `Todo`는 할 일 한 개의 설계도입니다.
- `new Todo("공부")`: 설계도로 실제 객체를 만듭니다.
- 필드: 객체가 가진 값입니다. `title`, `completed`가 해당합니다.
- 메서드: 객체가 수행하는 동작입니다. `update(...)`가 해당합니다.
- 생성자: 객체가 만들어질 때 실행하는 코드입니다. 클래스 이름과 같습니다.
- `private`: 클래스 바깥에서 필드를 직접 바꾸지 못하게 합니다.
- getter/setter: 값을 읽고 쓰는 메서드입니다. 스프링의 폼 입력 연결과 템플릿에서도 사용합니다.
- `Long`: 정수 값을 담는 타입이며 `null`도 가능합니다. 저장 전에는 `id`가 없습니다.
- `boolean`: `true` 또는 `false`입니다.
- `List<Todo>`: 여러 할 일을 담은 목록입니다.
- `interface`: 제공할 동작의 규약입니다. Repository 구현은 Spring Data JPA가 맡습니다.
- `final`: 해당 필드에 다른 객체를 다시 대입하지 못하게 합니다.
- `package`/`import`: 클래스의 소속과 다른 클래스를 가져오는 선언입니다.

## 4. 프로젝트 구성과 의존성

`pom.xml`은 필요한 라이브러리와 빌드 설정을 선언합니다. Maven은 이 파일을 읽어 라이브러리를 내려받고 코드를 컴파일합니다. `mvnw`는 정해진 Maven을 실행하는 도우미입니다.

| 라이브러리 | 역할 |
|---|---|
| spring-boot-starter-webmvc | HTTP 요청, 컨트롤러, 내장 웹 서버 |
| spring-boot-starter-thymeleaf | HTML에 Java 데이터 연결 |
| spring-boot-starter-data-jpa | 객체를 통한 DB 접근 |
| h2 | 별도 설치 없이 실행하는 DB |
| spring-boot-starter-validation | 입력값 검증 |
| spring-boot-h2console | 브라우저에서 DB 확인 |
| 이름이 -test로 끝나는 의존성 | 테스트 지원 |

Spring Boot는 라이브러리와 설정을 보고 기본 구성을 자동으로 준비합니다. 아래 코드는 Spring Boot 4.1.1 기준이며, 예전 강의의 `javax.persistence` 대신 `jakarta.persistence`를 사용합니다.

```text
src/main/java/com/example/todolearning/
  TodoLearningApplication.java   시작점
  todo/
    Todo.java                   DB에 저장할 객체
    TodoForm.java               화면 입력
    TodoRepository.java         DB 접근
    TodoNotFoundException.java  없는 데이터 처리
    TodoService.java            작업 단위
    TodoController.java         URL 처리
src/main/resources/
  application.properties        DB와 서버 설정
  templates/todos/              목록·등록·수정 HTML
  templates/error/404.html      오류 화면
  static/css/style.css          디자인
src/test/java/                  테스트
```

처음부터 생성하려면 [Spring Initializr](https://start.spring.io)에서 Maven, Java 21, Spring Web, Thymeleaf, Spring Data JPA, H2 Database, Validation을 선택합니다. 이 폴더에는 이미 생성과 코드 작성을 마쳤습니다.

## 5. 첫 번째 파일: 앱 시작하기

## 6. DB 연결 설정하기

DB는 데이터를 저장하는 프로그램이고, 테이블은 행과 열로 데이터를 정리한 공간입니다. `TODO` 테이블에는 `ID`, `TITLE`, `COMPLETED` 열이 만들어집니다.

`jdbc:h2:file:./data/todos`는 H2 파일 DB의 주소입니다. `jdbc`는 Java의 DB 연결 방식을 가리키고, `file`은 디스크 저장 방식을 뜻합니다. 이 주소는 웹 브라우저 주소가 아닙니다.


파일: `src/main/resources/application.properties`

```properties
spring.application.name=todo-learning
# 개인 PC에서 학습하는 예제입니다.
server.address=127.0.0.1

# 프로젝트 폴더 아래 data/에 저장하여 서버를 재시작해도 유지합니다.
spring.datasource.url=jdbc:h2:file:./data/todos
spring.datasource.username=sa
spring.datasource.password=

# 학습용 자동 테이블 생성/변경. 운영에서는 마이그레이션 도구를 사용합니다.
spring.jpa.hibernate.ddl-auto=update
spring.jpa.open-in-view=false
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# 로컬 학습용 DB 확인 화면
spring.h2.console.enabled=true
spring.h2.console.path=/h2-console
spring.h2.console.settings.web-allow-others=false
```

`ddl-auto=update`를 설정하면 Hibernate가 엔티티 정보를 보고 테이블 생성·변경을 시도합니다. 모든 스키마 변경을 안전하게 처리하는 기능은 아니므로 운영에서는 Flyway 같은 마이그레이션 도구를 사용합니다. `create` 또는 `create-drop`으로 바꾸면 기존 데이터가 사라질 수 있습니다.

`show-sql=true`로 DB에 실행되는 SQL을 서버 터미널에서 볼 수 있습니다. `open-in-view=false`는 화면 렌더링까지 JPA 영속성 컨텍스트를 계속 열어 두지 않도록 합니다. 지금은 단순 필드만 사용하므로 서비스가 반환한 값을 화면에서 바로 읽을 수 있습니다.

## 7. Entity: 저장할 데이터 정의하기

`Todo` 객체 한 개를 DB 테이블 한 행에 대응시킵니다. JPA는 Java 객체와 관계형 DB를 연결하는 표준이고, Hibernate는 그 표준을 실제로 구현합니다. Spring Data JPA는 그 위에서 Repository 작성량을 줄여 줍니다. DB 자체가 JPA인 것은 아닙니다.


파일: `src/main/java/com/example/todolearning/todo/Todo.java`

```java
package com.example.todolearning.todo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

// 자바 객체를 DB 테이블의 한 행과 연결합니다.
@Entity
public class Todo {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(nullable = false)
    private boolean completed;

    // JPA가 DB 데이터를 객체로 만들 때 사용하는 기본 생성자입니다.
    protected Todo() {
    }

    public Todo(String title) {
        this.title = title;
        this.completed = false;
    }

    public void update(String title, boolean completed) {
        this.title = title;
        this.completed = completed;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public boolean isCompleted() { return completed; }
}
```

- `@Entity`: 이 클래스를 JPA가 관리하는 엔티티로 등록합니다.
- `@Id`: 각 행을 구분하는 기본 키입니다. 제목이 같아도 ID로 다른 할 일을 구별합니다.
- `@GeneratedValue`: 기본 키 생성 방식을 정합니다. `IDENTITY`는 DB의 자동 증가 기능을 사용합니다.
- `@Column(nullable=false, length=100)`: 열의 제약을 정의합니다. `length`는 문자열 열에 적용합니다.
- `protected Todo()`: JPA가 객체를 복원할 때 필요한 기본 생성자입니다.

`@Column(nullable=false)`는 공백 문자열을 막는 규칙은 아닙니다. 공백 입력은 다음 단계의 검증으로 막습니다.

새 객체는 `completed=false`로 만들어지며, 저장하면 DB가 ID를 생성합니다. 전 필드의 setter를 만드는 대신 `update()`로 변경 가능한 내용을 명시했습니다.

## 8. Form/DTO: 입력값 받기와 검증

폼에서 들어오는 값은 `TodoForm`으로 받습니다. DTO는 데이터를 옮기는 객체라는 뜻입니다. DB 엔티티를 그대로 입력 대상으로 쓰면 사용자가 바꾸면 안 되는 필드까지 입력받기 쉬워집니다.


파일: `src/main/java/com/example/todolearning/todo/TodoForm.java`

```java
package com.example.todolearning.todo;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

// 화면 입력 전용 객체(DTO). DB 객체인 Todo와 역할을 구분합니다.
public class TodoForm {
    @NotBlank(message = "할 일을 입력해 주세요.")
    @Size(max = 100, message = "할 일은 100자 이내로 입력해 주세요.")
    private String title;

    private boolean completed;

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public boolean isCompleted() { return completed; }
    public void setCompleted(boolean completed) { this.completed = completed; }
}
```

`@NotBlank`는 null, 빈 문자열, 공백뿐인 문자열을 거부합니다. `@Size(max=100)`은 문자열 길이를 제한합니다. 어노테이션을 붙이는 것만으로 아무 때나 검증되지는 않습니다. 뒤에서 컨트롤러의 `@Valid`가 검증을 요청합니다.

HTML의 `required`와 `maxlength`는 사용자 편의를 위한 브라우저 검사입니다. 직접 HTTP 요청을 보낼 수도 있으므로 서버에서도 검사해야 합니다.

## 9. Repository: DB 읽고 쓰기


파일: `src/main/java/com/example/todolearning/todo/TodoRepository.java`

```java
package com.example.todolearning.todo;

import org.springframework.data.jpa.repository.JpaRepository;

// <관리할 엔티티, 기본 키 타입>. 구현체는 Spring Data JPA가 생성합니다.
public interface TodoRepository extends JpaRepository<Todo, Long> {
}
```

`JpaRepository<Todo, Long>`은 Todo 엔티티를 다루고 기본 키 타입은 Long이라는 뜻입니다. 일반 Java 인터페이스가 혼자 실행되는 것은 아닙니다. Spring Data JPA가 실행 시 구현체를 만들어 스프링에 등록합니다. 이 인터페이스에 `@Repository`를 추가하지 않아도 됩니다.

| Java 호출 | 개념상 SQL | 의미 |
|---|---|---|
| `save(new Todo("공부"))` | `INSERT INTO todo ...` | 새 행 저장 |
| `findAll()` | `SELECT ... FROM todo` | 전체 조회 |
| `findById(1L)` | `SELECT ... WHERE id = ?` | ID로 조회 |
| `delete(todo)` | `DELETE FROM todo WHERE id = ?` | 삭제 |

실제 SQL과 실행 시점은 엔티티 상태, 키 생성 방식, flush 시점 등에 따라 달라집니다. `save()`가 언제나 INSERT라는 뜻은 아닙니다. 위 표는 신규 객체 저장의 예입니다.

`findById()`는 `Optional<Todo>`를 반환합니다. 조회 결과가 없을 가능성을 표현하는 상자라고 생각하세요. 다음 서비스에서는 결과가 없으면 예외를 던집니다.

## 10. Service: 하나의 작업과 트랜잭션


파일: `src/main/java/com/example/todolearning/todo/TodoService.java`

```java
package com.example.todolearning.todo;

import java.util.List;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional(readOnly = true)
public class TodoService {
    private final TodoRepository todoRepository;

    // 생성자 주입: 스프링이 필요한 Repository를 넣어 줍니다.
    public TodoService(TodoRepository todoRepository) {
        this.todoRepository = todoRepository;
    }

    public List<Todo> findAll() {
        return todoRepository.findAll(Sort.by(Sort.Direction.DESC, "id"));
    }

    public Todo findById(Long id) {
        return todoRepository.findById(id)
                .orElseThrow(() -> new TodoNotFoundException(id));
    }

    @Transactional
    public void create(TodoForm form) {
        todoRepository.save(new Todo(form.getTitle().strip()));
    }

    @Transactional
    public void update(Long id, TodoForm form) {
        Todo todo = findById(id);
        todo.update(form.getTitle().strip(), form.isCompleted());
        // 트랜잭션 안에서 조회한 엔티티의 변경은 커밋 때 DB에 반영됩니다.
        // 이 동작을 변경 감지(dirty checking)라고 부릅니다.
    }

    @Transactional
    public void delete(Long id) {
        todoRepository.delete(findById(id));
    }
}
```

`@Service`를 붙이면 스프링이 이 객체를 생성해 관리합니다. 이렇게 관리되는 객체를 **빈(bean)**이라고 합니다.

생성자의 `TodoRepository`는 직접 `new`로 만들지 않습니다. 스프링이 이미 준비한 Repository를 전달합니다. 이를 **의존성 주입(DI)**이라고 합니다. 생성자가 하나이면 `@Autowired`를 생략할 수 있습니다.

트랜잭션은 여러 DB 변경을 하나의 작업으로 묶는 경계입니다. 예를 들어 계좌 이체에서는 출금만 되고 입금은 실패하는 상황을 막아야 합니다. 스프링의 기본 설정에서는 처리 중 RuntimeException이 밖으로 전파되면 롤백합니다. 모든 예외가 기본적으로 롤백되는 것은 아닙니다.

클래스의 `@Transactional(readOnly=true)`는 조회 중심의 기본 설정이고, 저장·수정·삭제 메서드의 `@Transactional`은 쓰기 작업 설정으로 덮어씁니다. `readOnly`는 최적화 힌트로, 접근 권한을 강제로 제한하는 보안 기능은 아닙니다.

수정 메서드에서는 `save()`를 다시 호출하지 않습니다. 트랜잭션 안에서 조회한 엔티티를 JPA가 관리하고 있어 값의 변화를 감지합니다. 커밋할 때 필요한 UPDATE가 반영됩니다. 아무 객체나 바꿨다고 저장되는 것은 아닙니다.

스프링 트랜잭션은 보통 프록시를 통해 적용됩니다. 이 예제는 컨트롤러가 서비스의 public 메서드를 호출하면서 경계가 시작됩니다. 같은 클래스 안의 메서드 호출만으로 새로운 트랜잭션 어노테이션이 적용되지는 않습니다.

## 11. 없는 데이터는 404로 처리하기


파일: `src/main/java/com/example/todolearning/todo/TodoNotFoundException.java`

```java
package com.example.todolearning.todo;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ResponseStatus;

@ResponseStatus(HttpStatus.NOT_FOUND)
public class TodoNotFoundException extends RuntimeException {
    public TodoNotFoundException(Long id) {
        super("할 일을 찾을 수 없습니다: " + id);
    }
}
```

`orElseThrow(() -> new TodoNotFoundException(id))`는 조회 결과가 없을 때 실행합니다. `() -> ...`는 필요할 때 실행할 동작을 전달하는 람다 문법입니다.

`@ResponseStatus(HttpStatus.NOT_FOUND)`는 이 예외를 HTTP 404에 연결합니다. 200은 성공, 302는 다른 주소로 이동, 404는 대상 없음, 500은 서버 내부 오류를 나타냅니다.

## 12. Controller: 주소와 Java 메서드 연결하기

컨트롤러는 요청의 입구입니다. 입력을 받고, 서비스에 작업을 부탁하고, 어떤 화면을 보여줄지 결정합니다.

| 요청 | 목적 |
|---|---|
| GET /todos | 목록 조회 |
| GET /todos/new | 등록 화면 |
| POST /todos | 등록 처리 |
| GET /todos/{id}/edit | 수정 화면 |
| POST /todos/{id}/edit | 수정 처리 |
| POST /todos/{id}/delete | 삭제 처리 |

GET은 조회에 사용합니다. 데이터를 변경하는 요청은 GET으로 만들지 않습니다. 기본 HTML 폼은 GET과 POST를 지원하므로 여기서는 수정·삭제도 POST로 처리합니다. JSON REST API에서는 PUT/PATCH/DELETE를 흔히 사용합니다.


파일: `src/main/java/com/example/todolearning/todo/TodoController.java`

```java
package com.example.todolearning.todo;

import jakarta.validation.Valid;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;

@Controller
public class TodoController {
    private final TodoService todoService;

    public TodoController(TodoService todoService) {
        this.todoService = todoService;
    }

    @GetMapping("/")
    public String home() {
        return "redirect:/todos";
    }

    @GetMapping("/todos")
    public String list(Model model) {
        model.addAttribute("todos", todoService.findAll());
        return "todos/list";
    }

    @GetMapping("/todos/new")
    public String newForm(Model model) {
        model.addAttribute("todoForm", new TodoForm());
        return "todos/new";
    }

    @PostMapping("/todos")
    public String create(@Valid @ModelAttribute("todoForm") TodoForm form,
                         BindingResult bindingResult) {
        // BindingResult는 검증 대상 매개변수 바로 다음에 둡니다.
        if (bindingResult.hasErrors()) {
            return "todos/new";
        }
        todoService.create(form);
        return "redirect:/todos";
    }

    @GetMapping("/todos/{id}/edit")
    public String editForm(@PathVariable("id") Long id, Model model) {
        Todo todo = todoService.findById(id);
        TodoForm form = new TodoForm();
        form.setTitle(todo.getTitle());
        form.setCompleted(todo.isCompleted());
        model.addAttribute("todoForm", form);
        model.addAttribute("todoId", id);
        return "todos/edit";
    }

    @PostMapping("/todos/{id}/edit")
    public String update(@PathVariable("id") Long id,
                         @Valid @ModelAttribute("todoForm") TodoForm form,
                         BindingResult bindingResult, Model model) {
        if (bindingResult.hasErrors()) {
            model.addAttribute("todoId", id);
            return "todos/edit";
        }
        todoService.update(id, form);
        return "redirect:/todos";
    }

    @PostMapping("/todos/{id}/delete")
    public String delete(@PathVariable("id") Long id) {
        todoService.delete(id);
        return "redirect:/todos";
    }
}
```

목록 메서드를 먼저 읽어 보세요.

```java
@GetMapping("/todos")
public String list(Model model) {
    model.addAttribute("todos", todoService.findAll());
    return "todos/list";
}
```

1. 브라우저가 GET /todos를 요청하면 `list()`가 실행됩니다.
2. 서비스에서 할 일 목록을 가져옵니다.
3. `Model`이라는 화면용 데이터 보관함에 `todos`라는 이름으로 넣습니다.
4. `todos/list`를 반환하면 Thymeleaf가 `templates/todos/list.html`을 렌더링합니다.

다음으로 등록 메서드를 읽어 보세요.

- `@ModelAttribute("todoForm")`: 폼의 이름과 객체 필드를 연결하고 모델에도 제공합니다.
- `@Valid`: TodoForm에 선언한 검증을 실행합니다.
- `BindingResult`: 검증 오류를 담습니다. 반드시 해당 입력 매개변수 바로 뒤에 둡니다.
- 오류가 있으면 등록 화면을 다시 보여줍니다. 입력값과 오류 정보가 유지됩니다.
- 성공하면 `redirect:/todos`를 반환합니다. 브라우저가 새로운 GET 요청으로 목록을 엽니다.

이 흐름을 Post/Redirect/Get이라고 합니다. 성공한 POST 화면을 새로고침할 때 같은 등록 요청을 다시 보내는 일을 줄입니다. 빠른 중복 클릭까지 모두 방지하는 기능은 아닙니다.

`@PathVariable("id")`는 `/todos/3/edit`에서 숫자 `3`을 받습니다. `@RequestParam`은 `/todos?keyword=공부`의 검색 조건 같은 쿼리 매개변수를 받을 때 사용합니다. `@RequestBody`는 JSON 요청 본문을 객체로 받을 때 사용하며, 이 HTML 폼 예제에는 필요하지 않습니다.

`@Controller`의 문자열 반환은 주로 화면 이름입니다. `@RestController`는 `@Controller`와 `@ResponseBody`를 합친 것으로, 반환값을 응답 본문에 씁니다. 객체는 보통 JSON으로 변환되고 문자열은 그 문자열 자체가 전달됩니다. 따라서 이 코드의 어노테이션만 RestController로 바꾸면 화면 대신 `todos/list`라는 글자가 나옵니다.

## 13. HTML: 실제로 보고 누르는 화면

Thymeleaf는 서버의 데이터를 HTML에 넣는 템플릿 엔진입니다. Java 코드에서 넣은 `todos`를 `${todos}`로 읽습니다.

### 목록 화면


파일: `src/main/resources/templates/todos/list.html`

```html
<!DOCTYPE html>
<html lang="ko" xmlns:th="http://www.thymeleaf.org">
<head><meta charset="UTF-8"><meta name="viewport" content="width=device-width, initial-scale=1"><title>할 일 목록</title><link rel="stylesheet" th:href="@{/css/style.css}"></head>
<body><main>
    <p class="eyebrow">나의 첫 Spring 웹</p>
    <h1>할 일 목록</h1>
    <p>작은 할 일 하나부터 기록해 보세요.</p>
    <a class="button" th:href="@{/todos/new}">새 할 일 등록</a>
    <p th:if="${#lists.isEmpty(todos)}" class="empty">아직 할 일이 없습니다. 첫 할 일을 등록해 보세요.</p>
    <ul class="todos">
        <li th:each="todo : ${todos}">
            <div><span class="badge" th:text="${todo.completed ? '완료' : '진행 중'}"></span>
                <strong th:text="${todo.title}"></strong></div>
            <div class="actions">
                <a th:href="@{/todos/{id}/edit(id=${todo.id})}">수정</a>
                <form th:action="@{/todos/{id}/delete(id=${todo.id})}" method="post">
                    <button class="delete" type="submit">삭제</button>
                </form>
            </div>
        </li>
    </ul>
</main></body></html>
```

- `th:each`: 목록만큼 반복합니다.
- `th:text`: 텍스트를 출력하며 HTML 특수문자를 이스케이프합니다. 입력한 `<script>`가 코드로 실행되지 않게 합니다.
- `th:if`: 조건이 맞을 때만 표시합니다.
- `th:href`와 `th:action`: 링크와 폼 전송 주소를 만듭니다.
- `@{/todos/{id}/edit(id=${todo.id})}`: 실제 ID가 들어간 주소를 생성합니다.

### 등록 화면


파일: `src/main/resources/templates/todos/new.html`

```html
<!DOCTYPE html>
<html lang="ko" xmlns:th="http://www.thymeleaf.org">
<head><meta charset="UTF-8"><meta name="viewport" content="width=device-width, initial-scale=1"><title>할 일 등록</title><link rel="stylesheet" th:href="@{/css/style.css}"></head>
<body><main>
    <p class="eyebrow">CREATE · 등록</p><h1>새 할 일</h1>
    <form th:action="@{/todos}" th:object="${todoForm}" method="post">
        <label for="title">할 일</label>
        <input id="title" type="text" th:field="*{title}" maxlength="100" required placeholder="예: 컨트롤러 역할 이해하기" aria-describedby="title-error">
        <p id="title-error" class="error" th:if="${#fields.hasErrors('title')}" th:errors="*{title}"></p>
        <div class="actions"><button type="submit">저장</button><a th:href="@{/todos}">취소</a></div>
    </form>
</main></body></html>
```

`th:object="${todoForm}"`은 이 폼이 사용할 객체입니다. `th:field="*{title}"`은 해당 객체의 title과 입력을 연결하며 name, id, value 등을 생성합니다. 폼을 제출하면 title이라는 이름으로 입력값이 전송됩니다.

`th:errors`는 서버 검증 오류를 출력합니다. 이 예제는 검증 실패 시 HTML 화면을 200으로 다시 보여줍니다. 검증 오류를 반드시 400으로 응답해야 하는 것은 아닙니다. JSON API에서는 400과 오류 JSON을 흔히 사용합니다.

### 수정 화면


파일: `src/main/resources/templates/todos/edit.html`

```html
<!DOCTYPE html>
<html lang="ko" xmlns:th="http://www.thymeleaf.org">

<body><main>
    <p class="eyebrow">UPDATE · 수정</p><h1>할 일 수정</h1>
    <form th:action="@{/todos/{id}/edit(id=${todoId})}" th:object="${todoForm}" method="post">
```

## 14. 어노테이션 한눈에 보기

어노테이션은 `@`로 붙이는 메타데이터입니다. 표시만으로 마법처럼 모든 것이 실행되는 것은 아니고, 스프링·JPA·검증 라이브러리가 이를 읽고 동작을 적용합니다. Java의 `@Override`처럼 컴파일러가 확인하는 어노테이션도 있습니다.

| 어노테이션 | 읽는 쪽 | 역할 |
|---|---|---|
| @SpringBootApplication | Spring Boot | 시작 설정, 자동 설정, 컴포넌트 탐색 |
| @Controller | Spring MVC | 화면 요청 처리 빈 |
| @Service | Spring | 서비스 빈 등록 |
| @GetMapping / @PostMapping | Spring MVC | HTTP 메서드와 경로 연결 |
| @PathVariable | Spring MVC | URL 경로 변수 연결 |
| @ModelAttribute | Spring MVC | 폼 입력 연결, 모델 제공 |
| @Valid | 검증 연동 | 객체의 검증 규칙 실행 요청 |
| @NotBlank / @Size | Bean Validation | 공백 및 길이 제약 |
| @Transactional | Spring 트랜잭션 | 작업의 트랜잭션 경계 |
| @Entity | JPA | 영속 엔티티 선언 |
| @Id / @GeneratedValue | JPA | 기본 키와 생성 방식 |
| @Column | JPA | 열 매핑과 제약 |
| @ResponseStatus | Spring MVC | 응답 상태 코드 지정 |

Entity가 자동으로 Service와 같은 스프링 빈이 되는 것은 아닙니다. 엔티티 인스턴스의 영속 상태는 JPA가 관리하고, Controller와 Service의 객체 생명주기는 스프링 컨테이너가 관리합니다.

## 16. 테스트는 왜 필요할까요?

컴파일 성공은 문법과 타입 검사를 통과했다는 뜻입니다. 실제 요청이 올바른 테이블 변경으로 이어지는지까지 보장하지는 않습니다.

```sh
./mvnw test
```

`TodoWebIntegrationTests`는 실제 임시 포트의 서버로 HTTP 요청을 보냅니다. 등록 → 조회 → 수정 → 완료 해제 → 삭제, 공백·길이 검증, 없는 ID, 출력 이스케이프를 검사합니다. 테스트 DB는 메모리 기반이어서 학습 중 저장한 파일 DB에 영향을 주지 않습니다.

## 17. 다음에는 무엇을 만들까요?

한 번에 전부 외우기보다 다음 순서로 확장해 보세요.

1. **설명 필드 추가**: Entity → Form → Service → HTML에 description 추가. 값이 어디를 지나가는지 익힙니다.
2. **검색**: Repository에 `findByTitleContaining(String keyword)`를 선언하고 Controller에서 `@RequestParam`으로 검색어를 받습니다. Spring Data가 메서드 이름을 해석합니다.
3. **페이징**: 모든 데이터를 한 번에 읽는 대신 Pageable과 Page로 나눕니다.
4. **JSON API**: 별도의 RestController에서 DTO를 반환하고 화면과 서버를 분리해 봅니다.
5. **로그인·권한**: Spring Security로 사용자를 구분하고 본인의 할 일만 변경하도록 검증합니다. 비밀번호는 직접 평문 저장하지 않습니다.
6. **운영 DB**: MySQL/PostgreSQL 드라이버와 연결 설정, 환경변수, 마이그레이션을 익힙니다. DB를 바꾸면 SQL과 타입 차이도 확인해야 합니다.

현재 예제는 인증과 CSRF 보호를 포함하지 않는 로컬 학습용입니다. 사용자별 권한과 외부 공개 설정은 위 확장 단계에서 다룹니다.

      <h2 class="section-title">1. Spring이란 무엇인가</h2>
      <p>
        Spring은 Java 진영에서 가장 널리 쓰이는 애플리케이션 프레임워크로, 객체 간의 결합도를 낮추고
        재사용 가능하고 테스트하기 쉬운 코드를 작성할 수 있도록 도와주는 것이 핵심 목표입니다.
        전통적인 Java 개발에서는 개발자가 직접 <code>new</code> 키워드로 객체를 생성하고 의존 관계를 맺어야 했지만,
        Spring은 이 과정을 프레임워크가 대신 처리해주는 <b>제어의 역전(IoC)</b> 구조를 기반으로 합니다.
      </p>
      <div class="callout tip">
        <b>Spring Framework vs Spring Boot</b><br>
        Spring Framework는 IoC/DI, AOP, MVC 등 핵심 기능을 제공하는 '엔진'이고,
        Spring Boot는 이 엔진 위에서 복잡한 XML 설정 없이 빠르게 프로젝트를 시작할 수 있도록 자동 설정(Auto Configuration)과
        내장 톰캣(Embedded Tomcat) 등을 제공하는 '스타터 패키지'입니다. 실무에서는 거의 항상 Spring Boot를 사용합니다.
      </div>

      <h3 id="ioc-di">1-1. IoC (제어의 역전)와 DI (의존성 주입)</h3>
      <p>
        <b>IoC(Inversion of Control)</b>는 객체의 생성과 생명주기 관리 권한을 개발자가 아닌 프레임워크(Spring Container)가
        갖는 설계 원칙입니다. 개발자는 필요한 객체를 직접 만들지 않고, 컨테이너가 만들어 둔 객체를 '주입'받아 사용합니다.
        이 주입 과정을 <b>DI(Dependency Injection)</b>라고 부릅니다.
      </p>
      <p>DI에는 세 가지 방식이 있습니다.</p>
      <table>
        <tr><th>방식</th><th>특징</th><th>권장 여부</th></tr>
        <tr>
          <td>생성자 주입</td>
          <td>객체 생성 시점에 필요한 의존성을 모두 주입. 필드를 <code>final</code>로 선언 가능</td>
          <td>✅ 가장 권장됨 (순환 참조를 컴파일 타임에 방지, 불변성 보장)</td>
        </tr>
        <tr>
          <td>수정자(Setter) 주입</td>
          <td><code>setXxx()</code> 메서드를 통해 주입. 선택적 의존성에 적합</td>
          <td>△ 필수 의존성에는 비권장</td>
        </tr>
        <tr>
          <td>필드 주입</td>
          <td><code>@Autowired</code>를 필드에 직접 붙임. 코드가 짧지만 테스트가 어려움</td>
          <td>❌ 비권장 (외부에서 의존성 교체 불가)</td>
        </tr>
      </table>
      <pre><code><span class="cm">// 생성자 주입 (권장 방식) — Lombok의 @RequiredArgsConstructor와 함께 자주 사용</span>

      <h3 id="aop">1-3. AOP (관점 지향 프로그래밍)</h3>
      <p>
        <b>AOP(Aspect-Oriented Programming)</b>는 로깅, 트랜잭션, 보안 검사처럼 여러 클래스에 공통적으로 필요한
        <b>횡단 관심사(Cross-cutting Concern)</b>를 핵심 비즈니스 로직과 분리해서 모듈화하는 기법입니다.
        대표적인 예가 <code>@Transactional</code>인데, 실제로는 프록시 객체가 메서드 호출 전후에 트랜잭션을
        시작/커밋/롤백하는 코드를 자동으로 감싸주는 방식으로 동작합니다.
      </p>
      <table>
        <tr><th>용어</th><th>설명</th></tr>

        <tr><td>Advice</td><td>실제로 실행되는 부가 기능 코드 (Before, After, Around 등)</td></tr>
        <tr><td>Join Point</td><td>Advice가 적용될 수 있는 지점 (메서드 실행 시점 등)</td></tr>
        <tr><td>Pointcut</td><td>Join Point 중 실제로 Advice를 적용할 대상을 선별하는 표현식</td></tr>
        <tr><td>Proxy</td><td>Spring이 AOP 구현을 위해 생성하는 대리 객체</td></tr>
      </table>

    <section id="jpa-basic">
      <h2 class="section-title">2. JPA 연동</h2>
      <p>
        <b>JPA(Java Persistence Association)</b>는 자바 객체와 관계형 데이터베이스 테이블을 매핑해주는
        <b>ORM(Object-Relational Mapping)</b> 표준 명세입니다. JPA 자체는 인터페이스 모음이고,
        실제 구현체로 Hibernate가 가장 널리 쓰입니다. Spring Boot 프로젝트에서는 보통
        <code>spring-boot-starter-data-jpa</code> 의존성을 추가해 Hibernate + Spring Data JPA를 함께 사용합니다.
      </p>
      <div class="callout">
        <b>왜 JPA를 쓰는가?</b><br>
        SQL을 직접 작성하지 않고 객체 중심으로 개발할 수 있어 생산성이 높고, DB 방언(Dialect)이 추상화되어
        DB를 교체하기 쉬우며, 1차 캐시·지연 로딩 등 성능 최적화 기능을 기본 제공합니다.
      </div>

      <h3>기본 Entity 매핑 예시</h3>
      <pre><code><span class="an">@Entity</span>
<span class="an">@Table</span>(name = <span class="str">"members"</span>)
<span class="kw">public class</span> <span class="ty">Member</span> {

    <span class="an">@Id</span>
    <span class="an">@GeneratedValue</span>(strategy = GenerationType.IDENTITY)
    <span class="kw">private</span> <span class="ty">Long</span> id;

    <span class="an">@Column</span>(nullable = <span class="kw">false</span>, length = 50)
    <span class="kw">private</span> <span class="ty">String</span> name;

    <span class="an">@Column</span>(unique = <span class="kw">true</span>)
    <span class="kw">private</span> <span class="ty">String</span> email;

    <span class="an">@Enumerated</span>(EnumType.STRING)
    <span class="kw">private</span> <span class="ty">Role</span> role;
}</code></pre>

      <h3 id="persistence-context">2-2. 영속성 컨텍스트 (Persistence Context)</h3>
      <p>
        JPA의 핵심 개념 중 하나가 <b>영속성 컨텍스트</b>입니다. <code>EntityManager</code>가 관리하는
        논리적인 공간으로, 여기에 저장된 엔티티는 '영속(Managed)' 상태가 되어 여러 이점을 얻습니다.
      </p>
      <table>
        <tr><th>엔티티 생명주기 상태</th><th>설명</th></tr>
        <tr><td>비영속 (New/Transient)</td><td><code>new</code>로 막 생성되어 영속성 컨텍스트와 무관한 상태</td></tr>
        <tr><td>영속 (Managed)</td><td><code>persist()</code>로 저장되어 영속성 컨텍스트가 관리하는 상태</td></tr>
        <tr><td>준영속 (Detached)</td><td>영속성 컨텍스트에서 분리된 상태 (<code>detach()</code>, 트랜잭션 종료 등)</td></tr>
        <tr><td>삭제 (Removed)</td><td><code>remove()</code>로 삭제가 예약된 상태</td></tr>
      </table>
      <p>영속성 컨텍스트가 제공하는 대표 기능:</p>
      <ul>
        <li><b>1차 캐시</b>: 같은 트랜잭션 내에서 동일 엔티티를 다시 조회하면 DB 접근 없이 캐시에서 반환</li>
        <li><b>동일성 보장</b>: 같은 트랜잭션 안에서 동일 PK로 조회한 엔티티는 항상 <code>==</code>로 같음</li>
        <li><b>쓰기 지연(Write-Behind)</b>: <code>persist()</code> 즉시 INSERT SQL을 날리지 않고 커밋 시점에 모아서 실행</li>
        <li><b>변경 감지(Dirty Checking)</b>: 트랜잭션 커밋 시점에 엔티티의 처음 상태(스냅샷)와 비교해 변경분만 UPDATE</li>
        <li><b>지연 로딩(Lazy Loading)</b>: 연관된 엔티티를 실제 사용 시점까지 조회를 미룸</li>
      </ul>
      <pre><code><span class="cm">// Dirty Checking 예시 — 별도의 save() 호출 없이도 UPDATE가 반영됨</span>
<span class="an">@Transactional</span>
<span class="kw">public void</span> updateName(<span class="ty">Long</span> id, <span class="ty">String</span> newName) {
    <span class="ty">Member</span> member = memberRepository.findById(id).orElseThrow();
    member.setName(newName); <span class="cm">// 트랜잭션 커밋 시점에 변경 감지되어 자동 UPDATE</span>
}</code></pre>

      <h3 id="jpa-relations">2-3. 연관관계 매핑</h3>
      <p>객체는 참조(주소값)로 연관관계를 표현하지만, 테이블은 외래키(FK)로 연관관계를 표현합니다.
        이 차이를 메꿔주는 것이 JPA의 연관관계 매핑 어노테이션입니다.</p>
      <table>
        <tr><th>어노테이션</th><th>관계</th><th>예시</th></tr>
        <tr><td><code>@ManyToOne</code></td><td>N:1 (연관관계의 주인, FK 보유)</td><td>주문(N) → 회원(1)</td></tr>
        <tr><td><code>@OneToMany</code></td><td>1:N (보통 주인이 아님, <code>mappedBy</code> 사용)</td><td>회원(1) → 주문(N)</td></tr>
        <tr><td><code>@OneToOne</code></td><td>1:1</td><td>회원(1) → 회원상세정보(1)</td></tr>
        <tr><td><code>@ManyToMany</code></td><td>N:M (실무에서는 중간 테이블 엔티티로 풀어서 사용 권장)</td><td>학생 ↔ 강의</td></tr>
      </table>
      <pre><code><span class="an">@Entity</span>
<span class="kw">public class</span> <span class="ty">Order</span> {
    <span class="an">@Id</span> <span class="an">@GeneratedValue</span>
    <span class="kw">private</span> <span class="ty">Long</span> id;

    <span class="an">@ManyToOne</span>(fetch = FetchType.LAZY) <span class="cm">// 연관관계의 주인 (FK를 가진 쪽)</span>
    <span class="an">@JoinColumn</span>(name = <span class="str">"member_id"</span>)
    <span class="kw">private</span> <span class="ty">Member</span> member;
}

<span class="an">@Entity</span>
<span class="kw">public class</span> <span class="ty">Member</span> {
    <span class="an">@Id</span> <span class="an">@GeneratedValue</span>
    <span class="kw">private</span> <span class="ty">Long</span> id;

    <span class="an">@OneToMany</span>(mappedBy = <span class="str">"member"</span>) <span class="cm">// 읽기 전용, FK는 Order 테이블에 있음</span>
    <span class="kw">private</span> <span class="ty">List</span>&lt;<span class="ty">Order</span>&gt; orders = <span class="kw">new</span> ArrayList&lt;&gt;();
}</code></pre>
      <div class="callout danger">
        <b>연관관계의 주인 (Owner)</b><br>
        FK를 가진 쪽(보통 <code>@ManyToOne</code> 쪽)이 연관관계의 주인이 되어야 합니다.
        주인이 아닌 쪽(<code>mappedBy</code>가 붙은 쪽)에서 값을 변경해도 실제 FK에는 반영되지 않으므로,
        연관관계 편의 메서드를 만들어 항상 주인 쪽 값을 함께 세팅해주는 습관이 중요합니다.
      </div>

      <h3 id="fetch">2-4. Fetch 전략과 N+1 문제</h3>
      <table>
        <tr><th>전략</th><th>기본값</th><th>설명</th></tr>
        <tr><td><code>FetchType.EAGER</code></td><td><code>@ManyToOne</code>, <code>@OneToOne</code> 기본값</td><td>연관 엔티티를 즉시 함께 조회 (Join)</td></tr>
        <tr><td><code>FetchType.LAZY</code></td><td><code>@OneToMany</code>, <code>@ManyToMany</code> 기본값</td><td>프록시 객체로 두고 실제 접근 시점에 조회</td></tr>
      </table>
      <p>
        <b>N+1 문제</b>는 연관관계가 있는 엔티티를 조회할 때, 최초 1번의 쿼리(예: 회원 목록 조회) 이후
        각 결과에 대해 연관 엔티티를 조회하는 쿼리가 N번 추가로 발생하는 현상입니다. 특히 <code>EAGER</code> 전략에서
        컬렉션 조회 시 자주 발생하며, <code>LAZY</code>로 바꿔도 반복문 안에서 연관 엔티티에 접근하면 동일하게 발생합니다.
      </p>
      <div class="callout tip">
        <b>N+1 해결 방법</b>
        <ul style="margin:8px 0 0;">
          <li><code>fetch join</code>: JPQL에서 <code>join fetch</code>로 한 번의 쿼리에 함께 조회</li>
          <li><code>@EntityGraph</code>: 특정 조회 메서드에서만 연관 엔티티를 함께 로딩하도록 지정</li>
          <li><code>batch size</code> 설정: <code>default_batch_fetch_size</code>로 IN 절을 묶어서 조회</li>
          <li>QueryDSL/DTO Projection으로 필요한 컬럼만 직접 조회</li>
        </ul>
      </div>

      <h3 id="spring-data-jpa">2-5. Spring Data JPA</h3>
      <p>
        <b>Spring Data JPA</b>는 JPA를 한 단계 더 추상화해서, Repository 인터페이스만 정의하면
        Spring이 런타임에 구현체를 자동 생성해주는 라이브러리입니다.
      </p>
      <pre><code><span class="kw">public interface</span> <span class="ty">MemberRepository</span> <span class="kw">extends</span> JpaRepository&lt;<span class="ty">Member</span>, <span class="ty">Long</span>&gt; {

    <span class="cm">// 메서드 이름만으로 쿼리가 자동 생성됨 (쿼리 메서드)</span>
    <span class="ty">Optional</span>&lt;<span class="ty">Member</span>&gt; findByEmail(<span class="ty">String</span> email);

    <span class="ty">List</span>&lt;<span class="ty">Member</span>&gt; findByNameContainingAndRole(<span class="ty">String</span> name, <span class="ty">Role</span> role);

    <span class="cm">// 복잡한 조회는 JPQL 직접 작성</span>
    <span class="an">@Query</span>(<span class="str">"select m from Member m join fetch m.orders where m.id = :id"</span>)
    <span class="ty">Optional</span>&lt;<span class="ty">Member</span>&gt; findWithOrders(<span class="an">@Param</span>(<span class="str">"id"</span>) <span class="ty">Long</span> id);
}</code></pre>
      <p>
        복잡한 동적 쿼리가 필요하면 <b>QueryDSL</b>을 함께 사용하는 것이 일반적입니다. QueryDSL은 타입 안전한
        Java 코드로 쿼리를 작성할 수 있어 오타나 타입 오류를 컴파일 타임에 잡을 수 있습니다.
      </p>

      <h3 id="transaction">2-6. 트랜잭션 관리</h3>
      <p>
        <code>@Transactional</code>은 메서드(또는 클래스) 실행을 하나의 트랜잭션으로 묶어줍니다.
        메서드가 정상 종료되면 커밋, 런타임 예외가 발생하면 자동 롤백됩니다.
      </p>
      <pre><code><span class="an">@Transactional</span>(readOnly = <span class="kw">true</span>) <span class="cm">// 조회 전용: 성능 최적화(변경 감지 생략) + 안전성</span>
<span class="kw">public</span> <span class="ty">MemberDto</span> getMember(<span class="ty">Long</span> id) { ... }

<span class="an">@Transactional</span> <span class="cm">// 쓰기 작업: 기본적으로 RuntimeException 발생 시 롤백</span>
<span class="kw">public void</span> transfer(<span class="ty">Long</span> fromId, <span class="ty">Long</span> toId, <span class="ty">int</span> amount) { ... }</code></pre>
      <table>
        <tr><th>속성</th><th>설명</th></tr>
        <tr><td><code>readOnly</code></td><td>조회 전용 트랜잭션 여부. <code>true</code>면 Dirty Checking 생략 등 최적화 적용</td></tr>
        <tr><td><code>rollbackFor</code></td><td>지정한 예외 발생 시 롤백 (기본은 RuntimeException/Error만 롤백)</td></tr>
        <tr><td><code>propagation</code></td><td>트랜잭션 전파 방식. <code>REQUIRED</code>(기본), <code>REQUIRES_NEW</code> 등</td></tr>
        <tr><td><code>isolation</code></td><td>트랜잭션 격리 수준 (READ_COMMITTED 등)</td></tr>
      </table>
    </section>

    <section id="jwt-structure">
      <h2 class="section-title">3. 토큰 기반 인증 (JWT)</h2>
      <p>
        세션 기반 인증은 서버가 세션 저장소에 로그인 상태를 저장해야 해서 서버를 여러 대로 확장(Scale-out)할 때
        세션 공유 문제가 생깁니다. <b>JWT(JSON Web Token)</b>는 서버가 상태를 저장하지 않고(Stateless),
        토큰 자체에 사용자 정보를 담아 클라이언트가 들고 다니게 하는 방식으로 이 문제를 해결합니다.
      </p>
      <h3>JWT 구조: Header.Payload.Signature</h3>
      <div class="diagram">
        <svg viewBox="0 0 900 130" xmlns="http://www.w3.org/2000/svg">
          <g font-family="sans-serif" font-size="13" fill="#e6e8f0">
            <rect x="10" y="20" width="260" height="70" rx="8" fill="#1c2030" stroke="#fbbf24"/>
            <text x="140" y="45" text-anchor="middle" fill="#fbbf24" font-weight="bold">HEADER</text>
            <text x="140" y="65" text-anchor="middle" font-size="11" fill="#9aa0b4">alg (HS256), typ (JWT)</text>

            <rect x="320" y="20" width="260" height="70" rx="8" fill="#1c2030" stroke="#7dd3fc"/>
            <text x="450" y="45" text-anchor="middle" fill="#7dd3fc" font-weight="bold">PAYLOAD</text>
            <text x="450" y="65" text-anchor="middle" font-size="11" fill="#9aa0b4">sub, role, iat, exp 등 claims</text>

            <rect x="630" y="20" width="260" height="70" rx="8" fill="#1c2030" stroke="#f87171"/>
            <text x="760" y="45" text-anchor="middle" fill="#f87171" font-weight="bold">SIGNATURE</text>
            <text x="760" y="65" text-anchor="middle" font-size="11" fill="#9aa0b4">HMAC(Header+Payload, 비밀키)</text>

            <text x="290" y="60" text-anchor="middle" font-size="20" fill="#6b7280">.</text>
            <text x="600" y="60" text-anchor="middle" font-size="20" fill="#6b7280">.</text>
          </g>
        </svg>
      </div>
      <ul>
        <li><b>Header</b>: 토큰 타입과 서명 알고리즘 정보 (Base64Url 인코딩)</li>
        <li><b>Payload</b>: 사용자 식별자(sub), 권한(role), 만료시간(exp) 등의 클레임. <b>암호화가 아니라 인코딩</b>이므로 민감정보는 절대 넣으면 안 됨</li>
        <li><b>Signature</b>: Header+Payload를 서버의 비밀키로 서명한 값. 토큰이 변조되지 않았음을 검증하는 용도</li>
      </ul>
      <div class="callout danger">
        <b>주의</b>: JWT는 발급 후에는 서버가 강제로 무효화하기 어렵습니다(Stateless 특성).
        그래서 만료 시간을 짧게 두고 Refresh Token으로 재발급하는 구조를 함께 씁니다.
      </div>

      <p>

        JWT 인증을 붙일 때는 보통 <code>UsernamePasswordAuthenticationFilter</code> 이전에
        커스텀 <code>JwtAuthenticationFilter</code>를 등록해서 세션이 아닌 토�큰 기반으로 인증 객체를 만듭니다.
      </p>
      <pre><code><span class="an">@Configuration</span>
<span class="an">@EnableWebSecurity</span>

    <span class="an">@Bean</span>
    <span class="kw">public</span> <span class="ty">SecurityFilterChain</span> filterChain(<span class="ty">HttpSecurity</span> http) <span class="kw">throws</span> <span class="ty">Exception</span> {
        http
            .csrf(csrf -&gt; csrf.disable()) <span class="cm">// 토큰 기반이면 CSRF 보호 불필요</span>

      <h3 id="refresh">3-4. Access Token / Refresh Token 전략</h3>
      <table>
        <tr><th>구분</th><th>Access Token</th><th>Refresh Token</th></tr>
        <tr><td>용도</td><td>API 요청 인증</td><td>Access Token 재발급</td></tr>
        <tr><td>수명</td><td>짧음 (보통 15분~1시간)</td><td>김 (보통 1주~2주)</td></tr>
        <tr><td>저장 위치</td><td>메모리 또는 짧은 만료의 쿠키</td><td>HttpOnly Secure 쿠키 또는 DB</td></tr>
        <tr><td>탈취 시 위험도</td><td>상대적으로 낮음(빨리 만료)</td><td>높음 (DB에 저장해 서버 측 폐기 가능하게 설계)</td></tr>
      </table>
      <div class="callout tip">
        <b>왜 두 토큰으로 나누는가?</b><br>
        Access Token만 쓰면 탈취 시 만료 전까지 계속 악용되고, 만료 시간을 짧게 하면 사용자가 자주 재로그인해야 합니다.
        Refresh Token을 별도로 두면 Access Token은 짧게 유지해 보안을 강화하면서도, 사용자는 재로그인 없이
        Refresh Token으로 새 Access Token을 계속 발급받아 편의성을 챙길 수 있습니다.
        Refresh Token은 DB(또는 Redis)에 저장해두고 로그아웃 시 폐기(Revoke) 처리하는 것이 일반적입니다.
      </div>
      <p>참고로 소셜 로그인이나 제3자 인증에는 <b>OAuth2</b> 프로토콜이 사용되며, Spring Security는
        <code>spring-boot-starter-oauth2-client</code>로 이를 지원합니다. OAuth2는 '인가(Authorization)' 프로토콜이고
        JWT는 그 결과로 발급되는 토큰의 '형식' 중 하나라는 점에서 서로 다른 층위의 개념입니다.</p>
    </section>

      <h3 id="anno-lombok">4-6. Lombok (자주 함께 사용) <span class="badge lombok">LOMBOK</span></h3>
      <p>Lombok은 Spring 자체 기능은 아니지만, 반복적인 getter/setter/생성자 코드를 어노테이션으로 자동 생성해줘서

      <table>
        <tr><th>어노테이션</th><th>설명</th></tr>
        <tr><td><code>@Getter</code> / <code>@Setter</code></td><td>모든 필드의 getter/setter 메서드 자동 생성</td></tr>
        <tr><td><code>@ToString</code></td><td><code>toString()</code> 메서드 자동 생성</td></tr>
        <tr><td><code>@EqualsAndHashCode</code></td><td><code>equals()</code>, <code>hashCode()</code> 자동 생성</td></tr>
        <tr><td><code>@NoArgsConstructor</code></td><td>파라미터 없는 기본 생성자 생성 (JPA 엔티티는 기본 생성자 필수)</td></tr>
        <tr><td><code>@AllArgsConstructor</code></td><td>모든 필드를 파라미터로 받는 생성자 생성</td></tr>
        <tr><td><code>@RequiredArgsConstructor</code></td><td><code>final</code> 필드만 파라미터로 받는 생성자 생성 (생성자 주입에 자주 활용)</td></tr>
        <tr><td><code>@Builder</code></td><td>빌더 패턴 코드 자동 생성 (가독성 좋은 객체 생성)</td></tr>
        <tr><td><code>@Data</code></td><td><code>@Getter</code>+<code>@Setter</code>+<code>@ToString</code>+<code>@EqualsAndHashCode</code>+<code>@RequiredArgsConstructor</code> 종합. 엔티티에는 비권장(양방향 연관관계에서 무한루프 위험)</td></tr>
        <tr><td><code>@Slf4j</code></td><td><code>log</code>라는 이름의 SLF4J Logger 인스턴스 자동 생성</td></tr>
      </table>
