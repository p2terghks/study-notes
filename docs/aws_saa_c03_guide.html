1. 보안 / 계정 관리 30%

1-1. IAM (Identity and Access Management)

AWS 리소스에 누가(Principal), 무엇에(Resource), 어떤 작업을(Action) 할 수 있는지 제어하는 글로벌 서비스입니다. 리전 개념이 없습니다.

구성 요소설명
User사람 또는 애플리케이션에 대응하는 개별 자격 증명. 액세스 키/비밀번호 보유
GroupUser의 묶음. 정책을 그룹 단위로 부여해 관리 효율화 (그룹은 다른 그룹을 포함할 수 없음)
Role임시 자격 증명을 발급받아 사용하는 '역할'. EC2·Lambda·크로스 계정 접근에 사용 (시험 핵심)
Policy권한을 정의한 JSON 문서. Identity 기반 / Resource 기반으로 구분

정책(Policy) JSON 구조

JSON · 설명용 주석 포함
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3ReadOnly",
      "Effect": "Allow",              // Allow 또는 Deny
      "Action": [                     // 허용할 API 작업
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [                   // 대상 리소스 ARN
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ],
      "Condition": {                  // 조건부 허용
        "IpAddress": { "aws:SourceIp": "203.0.113.0/24" },
        "Bool": { "aws:MultiFactorAuthPresent": "true" }
      }
    }
  ]
}
권한 평가 순서 (시험 빈출)
① 명시적 Deny가 하나라도 있으면 → 거부 (최우선, 무조건 이김)
② 명시적 Allow가 있으면 → 허용
③ 아무것도 없으면 → 암묵적 거부(Implicit Deny)
즉, "SCP에서 Deny, IAM에서 Allow" → 결과는 거부입니다.

IAM Role이 중요한 이유

EC2 인스턴스나 Lambda가 S3에 접근해야 할 때, 액세스 키를 코드에 하드코딩하거나 인스턴스에 저장하면 안 됩니다. 대신 IAM Role을 인스턴스 프로파일로 연결하면 STS가 임시 자격 증명을 자동 발급/교체해줍니다.

BASH
# EC2에 Role이 연결되면 메타데이터로 임시 자격 증명 확인 가능 (IMDSv2)
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

# 크로스 계정 접근: 다른 계정의 Role을 AssumeRole로 위임받음
aws sts assume-role \
  --role-arn "arn:aws:iam::222222222222:role/CrossAccountS3Role" \
  --role-session-name "chaehwan-session"
시험 포인트: "EC2가 S3에 접근해야 한다" → 정답은 항상 IAM Role 연결. 액세스 키를 인스턴스에 저장/환경변수 설정/AMI에 포함하는 선택지는 전부 오답입니다.

1-2. Organizations / SCP

개념설명
AWS Organizations여러 AWS 계정을 하나의 조직으로 묶어 중앙 관리. 통합 결제(Consolidated Billing) 제공
OU (Organizational Unit)계정을 용도별(Dev/Prod/Security)로 묶는 논리적 그룹
SCP (Service Control Policy)OU/계정에 적용되는 권한의 상한선(Guardrail). 권한을 부여하지 않고 제한만 함
AWS Control Tower멀티 계정 환경을 모범 사례에 맞춰 자동 구성 (Landing Zone)
SCP의 특징: 관리 계정(Management Account)에는 SCP가 적용되지 않습니다. 또한 SCP는 "허용"을 실제로 부여하지 않으며, IAM 정책과 SCP 모두에서 허용되어야 최종 허용됩니다.
통합 결제 이점: 여러 계정의 사용량을 합산해 볼륨 할인 티어에 도달하기 쉽고, RI/Savings Plans를 조직 내 계정 간 공유할 수 있습니다.
JSON · 설명용 주석 포함
// SCP 예시: 승인된 리전 외 사용 차단
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "NotAction": ["iam:*", "cloudfront:*", "route53:*"],  // 글로벌 서비스는 예외
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": ["ap-northeast-2", "us-east-1"]
      }
    }
  }]
}

1-3. KMS / Secrets Manager / 암호화

서비스용도시험 키워드
KMS암호화 키 생성·관리. 대부분의 AWS 서비스와 통합"저장 데이터 암호화", "키 관리"
CloudHSM전용 하드웨어 보안 모듈. 고객이 키를 단독 제어"FIPS 140-2 Level 3", "전용 HSM", "AWS도 키에 접근 불가"
Secrets ManagerDB 비밀번호 등 시크릿 저장 + 자동 교체(rotation)"자격 증명 자동 교체", "RDS 암호 로테이션"
Parameter Store설정값/시크릿 저장. 무료, 자동 교체 없음"저비용 설정 저장"
ACMSSL/TLS 인증서 무료 발급·자동 갱신 (ELB, CloudFront, API GW)"HTTPS 적용", "인증서 자동 갱신"
KMS 키 유형
· AWS 관리형 키: AWS가 자동 생성/관리, 무료, 연 1회 자동 교체
· 고객 관리형 키(CMK): 사용자가 정책·교체 주기 제어, 월 $1
· 고객 제공 키(BYOK): 외부에서 키 자료를 가져와 사용
Secrets Manager vs Parameter Store: 자동 교체가 필요하면 Secrets Manager, 단순 저장에 비용 절감이 목적이면 Parameter Store.

1-4. 보안 관련 서비스 정리

서비스역할계층
Security Group인스턴스 레벨 방화벽. Stateful, Allow 규칙만 존재인스턴스(ENI)
Network ACL서브넷 레벨 방화벽. Stateless, Allow/Deny 모두 가능, 규칙 번호 순 평가서브넷
AWS WAFL7(HTTP) 공격 차단. SQL 인젝션, XSS, Rate 제한CloudFront, ALB, API GW
AWS Shield Standard기본 DDoS 방어 (무료, 자동 적용)L3/L4
Shield Advanced고급 DDoS 방어 + DRT 지원 + 요금 급증 보호 (월 $3,000)L3/L4/L7
GuardDutyML 기반 위협 탐지. VPC Flow Logs, CloudTrail, DNS 로그 분석계정 전체
InspectorEC2/ECR/Lambda의 취약점(CVE) 스캔워크로드
MacieS3 내 개인정보(PII) 탐지 및 분류데이터
Security Hub여러 보안 서비스 결과를 통합 대시보드로 집계계정/조직
Detective보안 사고의 근본 원인 분석조사
SG vs NACL (단골 문제)
SG는 Stateful — 인바운드를 허용하면 아웃바운드 응답은 자동 허용됩니다.
NACL은 Stateless — 인바운드/아웃바운드 규칙을 양쪽 다 열어야 합니다. 특히 응답 트래픽을 위해 임시 포트(1024–65535) 아웃바운드 허용이 필요하다는 점이 자주 출제됩니다.
"특정 IP를 차단하고 싶다" → SG는 Deny 규칙이 없으므로 NACL이 정답입니다.

2-2. Auto Scaling Group (ASG)

워크로드에 따라 EC2 인스턴스 수를 자동으로 조절해 가용성과 비용 효율을 동시에 확보합니다. Min / Desired / Max 용량을 정의합니다.

스케일링 정책설명
Target Tracking특정 지표(예: 평균 CPU 50%)를 목표로 자동 조절. 가장 권장·간단
Step Scaling경보 수준에 따라 단계별로 다른 수의 인스턴스 추가/제거
Simple Scaling경보 발생 시 고정된 수만큼 조절 (쿨다운 대기 필요, 레거시)
Scheduled Scaling예측 가능한 시간대에 맞춰 조절 (예: 수강신청 오픈 10시)
Predictive ScalingML로 과거 패턴을 학습해 사전에 용량 확보
시험 포인트: "매주 금요일 오후에 트래픽이 급증한다" → Scheduled Scaling.
"트래픽 급증을 미리 대비해야 하고 패턴이 반복된다" → Predictive Scaling.
ASG는 여러 AZ에 걸쳐 구성해야 AZ 장애에 대비할 수 있습니다. 또한 ASG는 인스턴스 상태 확인 실패 시 자동 교체하므로 자가 치유(self-healing) 아키텍처의 핵심입니다.

3. 스토리지

3-1. S3 (Simple Storage Service)

무제한 용량의 객체 스토리지. 객체 하나당 최대 5TB, 버킷 이름은 전 세계적으로 고유해야 합니다. 기본 내구성은 99.999999999%(11 nines)입니다.

기능설명

3-3. EBS (Elastic Block Store)

EC2에 연결하는 네트워크 블록 스토리지. 기본적으로 단일 AZ에 종속되며, 다른 AZ로 옮기려면 스냅샷 → 새 AZ에 볼륨 생성 방식을 씁니다.

볼륨 타입특성용도
gp3SSD, 기본 3,000 IOPS / 125MB/s, 용량과 성능 독립 설정대부분의 워크로드 기본 선택 (gp2보다 저렴)
gp2SSD, 용량에 비례해 IOPS 증가 (3 IOPS/GB)레거시 범용
io1 / io2 Block ExpressSSD, 최대 256,000 IOPS, Multi-Attach 지원고성능 DB (SAP HANA, Oracle), 미션 크리티컬
st1HDD, 처리량 최적화빅데이터, 로그 처리, 데이터 웨어하우스
sc1HDD, 최저 비용접근 빈도가 매우 낮은 콜드 데이터
주의: HDD 계열(st1, sc1)은 부트 볼륨으로 사용할 수 없습니다. "IOPS가 매우 높아야 한다" → io1/io2, "처리량(Throughput)이 중요하다" → st1 또는 gp3.
Instance Store는 물리적으로 인스턴스에 부착된 임시 스토리지로, 성능은 최고지만 인스턴스 중지/종료 시 데이터가 소실됩니다. 캐시·버퍼·스크래치 용도로만 사용하세요.

5-1. RDS / Aurora

관리형 관계형 DB. 패치·백업·복구를 AWS가 담당하며, MySQL·PostgreSQL·MariaDB·Oracle·SQL Server·Aurora를 지원합니다.

기능Multi-AZ 배포Read Replica
목적고가용성 / 재해 복구읽기 성능 확장
복제 방식동기식 (Synchronous)비동기식 (Asynchronous)

Aurora

  • MySQL 대비 최대 5배, PostgreSQL 대비 3배 성능
  • 스토리지가 3개 AZ에 6개 복제본으로 자동 저장, 10GB 단위로 최대 128TB 자동 확장
  • 최대 15개의 Aurora Replica, 장애 조치 시간 30초 미만
  • Aurora Serverless v2: 트래픽에 따라 용량 자동 조절 → 간헐적·예측 불가 워크로드에 적합
  • Aurora Global Database: 리전 간 복제 지연 1초 미만, DR 시 1분 내 승격
시험 키워드: "간헐적으로만 사용하는 DB, 사용하지 않을 때 비용 최소화" → Aurora Serverless.
"전 세계 여러 리전에서 낮은 지연으로 읽기 + 리전 장애 대비" → Aurora Global Database.

서비스역할키워드
Redshift페타바이트급 데이터 웨어하우스(OLAP), 컬럼형 저장"복잡한 BI 분석 쿼리", "데이터 웨어하우스"
Redshift SpectrumS3 데이터를 로드 없이 직접 쿼리"S3의 대용량 데이터를 Redshift에서 조인"
AthenaS3에 대한 서버리스 SQL 쿼리. 스캔한 데이터량만 과금"인프라 없이 S3 로그를 즉석 분석", "비용 최소"
Glue서버리스 ETL + 데이터 카탈로그"스키마 검색", "데이터 변환 파이프라인"
EMRHadoop/Spark 관리형 클러스터"대규모 분산 빅데이터 처리", "Spark"
QuickSightBI 시각화 대시보드"대시보드", "시각화"
OpenSearch로그 검색·분석·시각화"전문 검색", "로그 분석 대시보드"
Athena vs Redshift: 임시·간헐적 쿼리에 서버 관리 없이 저비용이면 Athena, 지속적·복잡한 대규모 분석이면 Redshift. Athena는 Parquet/ORC 등 컬럼형 포맷 + 압축 + 파티셔닝으로 스캔량을 줄이는 것이 비용 최적화의 정답입니다.

6. 애플리케이션 통합

6-1. SQS (Simple Queue Service)

컴포넌트 간 결합도를 낮추는(decoupling) 메시지 큐. 생산자와 소비자가 서로를 몰라도 되며, 소비자 장애 시에도 메시지가 보존됩니다.

큐 유형순서처리량중복
Standard Queue최선 노력(순서 보장 X)사실상 무제한최소 1회 전달 (중복 가능)
FIFO Queue엄격한 순서 보장초당 300~3,000 메시지정확히 1회 처리
주요 개념설명
Visibility Timeout소비자가 메시지를 가져간 뒤 다른 소비자에게 보이지 않는 시간(기본 30초). 처리 시간보다 짧으면 중복 처리 발생
Dead Letter Queue (DLQ)지정 횟수 이상 처리 실패한 메시지를 격리해 분석
Long Polling메시지가 올 때까지 최대 20초 대기. 빈 응답 감소 → 비용 절감
Delay Queue메시지를 최대 15분 지연 후 소비 가능하게 함
메시지 보존기본 4일, 최대 14일
단골 문제: "메시지가 여러 번 처리되고 있다" → Visibility Timeout을 처리 시간보다 길게 설정.
"주문 처리 순서가 반드시 지켜져야 한다" → FIFO Queue.
"트래픽 급증 시 백엔드가 감당 못 함" → SQS를 앞에 두어 버퍼링(부하 평준화) + ASG가 큐 길이(ApproximateNumberOfMessages) 기준으로 스케일링.

6-2. SNS / EventBridge

서비스패턴용도
SNSPub/Sub 팬아웃하나의 메시지를 여러 구독자(SQS, Lambda, HTTP, 이메일, SMS)에 동시 전달
EventBridge이벤트 버스 + 규칙 기반 라우팅AWS 서비스 이벤트, SaaS 연동, 스케줄(cron) 실행
SNS + SQS 팬아웃 패턴: SNS 토픽에 여러 SQS 큐를 구독시키면, 하나의 이벤트를 여러 시스템이 각자의 속도로 독립 처리할 수 있습니다. 시험에 자주 나오는 아키텍처입니다.
"정해진 시간마다 Lambda 실행" → EventBridge Scheduler (구 CloudWatch Events).

6-3. Kinesis

서비스용도
Kinesis Data Streams실시간 스트리밍 데이터 수집. 샤드 단위, 데이터 1~365일 보존, 재처리 가능
Kinesis Data Firehose스트리밍 데이터를 S3·Redshift·OpenSearch로 자동 적재. 완전관리형, 준실시간(최소 60초 버퍼)
Kinesis Data Analytics스트림에 대해 실시간 SQL/Flink 분석
Kinesis Video Streams비디오 스트림 수집·저장
SQS vs Kinesis
· SQS: 메시지를 소비하면 삭제, 작업 큐(task queue) 성격, 소비자 수 제한 없음
· Kinesis: 데이터를 보존하며 여러 소비자가 반복 읽기, 순서 보장(샤드 내), 실시간 분석·로그 수집
"IoT 센서 수백만 건 실시간 수집 및 분석" → Kinesis Data Streams
"스트림 데이터를 코드 작성 없이 S3로 적재" → Firehose

6-4. Step Functions / API Gateway

서비스설명
Step Functions여러 Lambda·서비스를 상태 머신(워크플로)으로 오케스트레이션. 재시도·에러 처리·분기를 시각적으로 관리. 15분 초과 장기 실행 가능
API GatewayREST/HTTP/WebSocket API 관리. 인증(Cognito·IAM·Lambda Authorizer), 스로틀링, 캐싱, 사용량 계획
CognitoUser Pools(사용자 인증/회원가입), Identity Pools(AWS 리소스 접근용 임시 자격 증명)
AppSync관리형 GraphQL API. 실시간 구독, 오프라인 동기화
"여러 단계로 이루어진 복잡한 비즈니스 프로세스를 오류 처리와 재시도 포함해 조율" → Step Functions.
"모바일 앱 사용자 인증 + 소셜 로그인" → Cognito User Pool.
"API 호출량을 클라이언트별로 제한" → API Gateway 사용량 계획 + API 키.

7. 운영 / 아키텍처 설계

7-1. 모니터링 3종 세트 빈출

서비스무엇을 보는가시험 키워드
CloudWatch성능 지표·로그·알람 (CPU, 메모리, 디스크, 커스텀 지표)"모니터링", "임계값 알림", "로그 수집"
CloudTrailAPI 호출 기록 — 누가·언제·어디서·무엇을 했는가"누가 리소스를 삭제했는지 조사", "감사(audit)"
AWS Config리소스 구성 변경 이력 + 규정 준수 평가"규정 준수", "구성이 정책을 위반했는지", "변경 이력"
X-Ray분산 애플리케이션 요청 추적(트레이싱), 병목 구간 파악"마이크로서비스 성능 병목 분석"
절대 헷갈리면 안 되는 구분
· "누가 S3 버킷을 삭제했는가?" → CloudTrail
· "CPU 사용률이 80%를 넘으면 알림" → CloudWatch Alarm
· "모든 EBS 볼륨이 암호화되어 있는지 지속 확인" → AWS Config Rule
참고로 메모리 사용률과 디스크 사용량은 EC2 기본 지표가 아니어서 CloudWatch Agent 설치가 필요합니다. 이것도 자주 출제됩니다.

7-2. 고가용성 & 재해 복구 (DR)

전략RTO / RPO비용설명
Backup & Restore수 시간 ~ 일최저데이터만 백업. 장애 시 인프라를 새로 구축
Pilot Light수십 분낮음DB 등 핵심 코어만 켜두고 나머지는 꺼둠
Warm Standby수 분중간축소된 규모로 전체 스택 상시 가동, 장애 시 확장
Multi-Site Active/Active거의 0최고여러 리전에서 동시에 트래픽 처리
RTO(Recovery Time Objective): 복구까지 허용되는 시간
RPO(Recovery Point Objective): 허용되는 데이터 손실량(시점)
문제에서 "RTO/RPO를 몇 분 이내로" 같은 수치가 주어지면 위 표에서 대응되는 전략을 고르면 됩니다. "비용을 최소화하면서 DR" → Pilot Light, "거의 무중단" → Active/Active.

고가용성 설계 원칙

  • 다중 AZ 배포가 기본 — ALB + ASG + Multi-AZ RDS 조합
  • 단일 장애점(SPOF) 제거 — NAT Gateway도 AZ마다 배치
  • 무상태(Stateless) 설계 — 세션은 ElastiCache/DynamoDB로 외부화
  • 느슨한 결합 — SQS/SNS로 컴포넌트 분리
  • 상태 확인 기반 자동 복구 — ELB Health Check + ASG 자동 교체

8. 마무리 정리

8-1. 헷갈리는 서비스 비교 총정리

비교선택 기준
Multi-AZ vs Read Replica가용성 → Multi-AZ / 읽기 성능 → Read Replica
SG vs NACLStateful·Allow만 → SG / Stateless·Deny 가능 → NACL
ALB vs NLB경로 기반 라우팅·HTTP → ALB / 고정 IP·초저지연·TCP·UDP → NLB
CloudFront vs Global AcceleratorHTTP 캐싱 → CloudFront / 비HTTP·고정 IP → GA
SQS vs SNS1:1 큐잉·버퍼링 → SQS / 1:N 팬아웃 → SNS
SQS vs Kinesis처리 후 삭제 → SQS / 보존·다중 소비자·실시간 분석 → Kinesis
EFS vs EBS vs S3다중 EC2 공유 → EFS / 단일 EC2 블록 → EBS / 객체·정적파일 → S3
Athena vs Redshift간헐적 S3 쿼리 → Athena / 지속적 대규모 DW → Redshift
Secrets Manager vs Parameter Store자동 교체 필요 → Secrets Manager / 단순 저장·무료 → Parameter Store
KMS vs CloudHSM일반 암호화 → KMS / 전용 HSM·단독 키 제어 → CloudHSM
CloudTrail vs CloudWatch vs Config누가 했는가 → CloudTrail / 성능 지표 → CloudWatch / 구성 준수 → Config
DataSync vs Snowball네트워크 전송 → DataSync / 물리 배송(대용량·저대역폭) → Snowball
VPC Peering vs Transit Gateway소수 VPC 1:1 → Peering / 다수 VPC 허브 → TGW
Redis vs Memcached고가용성·영속성·리더보드 → Redis / 단순 캐시 → Memcached
Cluster vs Spread Placement저지연 HPC → Cluster / 장애 분산 → Spread

8-2. 시나리오 키워드 사전

8-3. 최종 점검 체크리스트

반드시 외울 숫자

  • Lambda 최대 실행 15분 / 메모리 10GB
  • S3 객체 최대 5TB, 멀티파트 5GB↑ 필수
  • SQS 메시지 보존 기본 4일, 최대 14일
  • Long Polling 최대 20초
  • Visibility Timeout 기본 30초
  • IA 계열 최소 보관 30일 / Glacier 90일 / Deep Archive 180일
  • Aurora 스토리지 6복제본 / 3 AZ, 최대 128TB
  • Aurora Replica 최대 15개, RDS Read Replica 최대 15개
  • VPC CIDR /16 ~ /28, 서브넷당 예약 IP 5개
  • 합격 점수 720/1000

오답으로 자주 등장하는 선택지

  • 액세스 키를 EC2/코드/AMI에 저장
  • 루트 계정으로 일상 작업 수행
  • 보안 그룹에 0.0.0.0/0 SSH 개방
  • EC2에 cron 스크립트를 짜서 직접 구현
  • Multi-AZ Standby에서 읽기 처리
  • Lambda로 15분 초과 작업 처리
  • HDD 볼륨(st1/sc1)을 부트 볼륨으로
  • VPC Peering의 전이적 라우팅 가정
  • Zone Apex에 CNAME 사용
  • DynamoDB 성능 문제에 ElastiCache 적용(→ DAX)
