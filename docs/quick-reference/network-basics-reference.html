REFERENCE 01

네트워크와 웹의 관계

네트워크는 장치들이 데이터를 주고받는 연결입니다. LAN은 집·사무실 같은 가까운 범위, WAN은 떨어진 네트워크를 연결하는 범위를 말합니다. 인터넷은 수많은 네트워크가 연결된 체계이고, 웹은 그 위에서 HTTP로 문서·API를 주고받는 서비스입니다. 인터넷에는 이메일·파일 전송 등도 있습니다.

클라이언트는 요청하는 역할, 서버는 요청을 받아 처리하는 역할입니다. 한 컴퓨터가 두 역할을 모두 할 수 있습니다. 웹 서버도 DB에 질의할 때는 DB의 클라이언트입니다.

REFERENCE 02

패킷과 계층: 역할을 나누어 이해하기

큰 데이터를 전송 단위로 나누고 각 계층의 주소·제어 정보를 붙여 전달합니다. 받는 쪽은 정보를 해석하고 데이터를 복원합니다. Ethernet의 전송 단위는 프레임, IP는 패킷, TCP는 세그먼트, UDP는 데이터그램이라고 부릅니다.

TCP/IP 관점 대표 역할·예 OSI 학습 모델과 대략 대응

REFERENCE 03

MAC·IP·포트·URL은 무엇이 다른가?

개념 역할 예
MAC 주소 같은 링크에서 인터페이스에 프레임 전달 Ethernet/Wi-Fi 인터페이스 주소
IP 주소 네트워크에서 출발지·목적지 식별과 경로 결정 192.168.1.10
포트 TCP/UDP에서 통신 끝점 구분 HTTPS 기본 443
소켓 프로그램이 통신에 사용하는 OS 인터페이스·자원 서버의 수신 소켓, 연결된 소켓
도메인 사람이 읽는 이름 example.com
URL 프로토콜·호스트·경로 등으로 자원 지정 https://example.com:443/docs?q=cpu

IP가 건물 주소라면 포트는 창구 번호에 가깝습니다. TCP 연결은 보통 출발지 IP·포트, 목적지 IP·포트와 프로토콜의 조합으로 구분합니다. TCP 53번과 UDP 53번은 별개입니다. 포트를 열어 둬도 라우팅·방화벽·서비스 실행 상태가 맞아야 접속됩니다.

REFERENCE 04

공인 IP·사설 IP·localhost

IPv4는 32비트, IPv6는 128비트 주소입니다. IPv6는 단순히 점 대신 콜론을 쓰는 IPv4가 아니며 주소·이웃 탐색 등에도 차이가 있습니다.

주소 의미
10.0.0.0/8 사설 IPv4 범위
172.16.0.0/12 172.16.0.0~`172.31.255.255` 사설 범위
192.168.0.0/16 사설 IPv4 범위
127.0.0.1 / ::1 자신에게 연결하는 IPv4 / IPv6 루프백
서버 바인딩의 0.0.0.0 모든 로컬 IPv4 인터페이스에서 수신

사설 주소는 인터넷에서 전역 경로로 직접 전달되지 않습니다. 공인 주소도 방화벽 등 때문에 접속할 수 없을 수 있습니다. 사설 주소가 아닌 주소가 전부 공인 주소인 것도 아닙니다. 루프백·링크 로컬 등 특수 범위가 있습니다.

localhost는 현재 실행 환경의 자기 자신입니다. 컨테이너 안의 localhost는 보통 호스트 PC나 다른 컨테이너가 아닙니다. 0.0.0.0은 서버의 수신 범위를 지정할 때 쓰며, 다른 PC에서 접속할 목적지로는 서버의 실제 IP·도메인을 사용합니다.

REFERENCE 05

서브넷과 CIDR: /24는 무엇인가?

192.168.10.0/24의 /24는 IPv4 주소 앞 24비트가 네트워크 부분이라는 뜻입니다. 나머지 8비트로 총 2^8 = 256개 주소를 표현합니다. 숫자가 커질수록 주소 범위는 작아집니다.

CIDR 전체 주소 수 범위 예
192.168.10.0/24 256 .0~`.255`
192.168.10.0/26 64 .0~`.63`
192.168.10.64/26 64 .64~`.127`

일반적인 IPv4 /24 서브넷에서 네트워크·브로드캐스트 주소를 빼면 호스트용 254개입니다. /31, /32 등에는 이 계산을 일괄 적용하지 않습니다. AWS VPC의 일반 IPv4 서브넷은 처음 4개와 마지막 1개를 예약하므로 /24에서 251개를 쓸 수 있습니다.

python
from ipaddress import ip_address, ip_network
network = ip_network("192.168.10.0/26")
print(network.num_addresses)  # 64: 전체 주소 수
print(network.broadcast_address)  # 192.168.10.63
print(ip_address("192.168.10.10") in network)  # True: 범위에 포함

REFERENCE 06

스위치·라우터·게이트웨이

  • 스위치: 보통 같은 LAN에서 MAC 주소를 보고 프레임을 전달합니다. 라우팅 기능을 갖춘 L3 스위치도 있습니다.
  • 라우터: 서로 다른 IP 네트워크 사이에서 경로를 선택합니다. 일반적으로 더 구체적인 목적지 경로가 우선합니다.
  • 기본 게이트웨이: 구체적인 경로가 없는 목적지로 나갈 때 사용하는 다음 경유지입니다.

같은 서브넷의 대상에는 직접 전달하고, 다른 네트워크의 대상에는 게이트웨이를 통해 전달하는 것이 기본 흐름입니다. 링크가 바뀌면 링크 계층 헤더도 바뀝니다. IP 주소는 일반 라우팅에서는 유지되지만 NAT를 지나면 바뀔 수 있습니다.

IPv4의 ARP는 같은 링크에서 IP에 해당하는 MAC을 찾는 데 쓰입니다. IPv6는 NDP를 사용합니다. DHCP는 IP·게이트웨이·DNS 서버 같은 설정을 자동 제공하는 역할이며 DNS 조회와는 다릅니다.

REFERENCE 08

TCP와 UDP: 전달 보장의 차이

구분 TCP UDP
형태 연결 기반 바이트 스트림 데이터그램 단위
순서·재전송 순서 보장·손실 재전송 기능 자체 순서·재전송 보장 없음
경계 앱 메시지 경계를 보존하지 않음 데이터그램 경계를 보존
사용 예 HTTP/1.1·HTTP/2, DB 연결 DNS, 실시간 전송, QUIC의 기반

TCP는 앱이 보낸 한 번의 메시지가 상대의 한 번의 읽기로 도착한다고 보장하지 않습니다. 길이·구분자 등의 메시지 규칙이 필요합니다. TCP 전송 보장이 결제·DB 저장 같은 업무 처리 성공까지 보장하는 것도 아닙니다.

UDP를 사용하는 앱도 필요한 신뢰성·혼잡 제어를 상위 프로토콜에서 구현할 수 있습니다. 따라서 “UDP는 언제나 빠르고 데이터 손실을 신경 쓰지 않는다”라고 외우면 부정확합니다.

TCP — RFC 9293 · UDP — RFC 768

REFERENCE 09

연결·TLS·HTTP 요청 흐름

새로운 HTTPS 연결을 HTTP/1.1 또는 HTTP/2로 만드는 단순화된 예입니다.

text
DNS로 주소 확인
→ TCP 연결: SYN → SYN+ACK → ACK
→ TLS 협상: 서버 인증·암호화 통신 준비
→ HTTP 요청: GET /docs
→ HTTP 응답: 상태 코드·헤더·본문

기존 연결·DNS 캐시를 재사용하면 일부 단계가 생략됩니다. HTTP/3는 TCP 대신 UDP 위의 QUIC을 사용합니다. HTTPS라고 항상 TCP를 쓰는 것은 아닙니다.

TLS는 통신 중 도청·변조를 막고 인증서를 통해 상대 서버의 신원을 검증하는 데 쓰입니다. 인증서가 있다고 웹앱의 내용이나 모든 기능이 안전하다는 뜻은 아닙니다.

HTTP 의미 — RFC 9110 · HTTP/3 — RFC 9114

HTTP 200이라도 본문에 업무 실패가 담길 수 있으므로 API 규약도 확인합니다. 쿠키는 브라우저가 저장하고 조건에 맞는 요청에 보내는 값입니다. 세션은 요청 사이에 유지하는 상태이며, 흔히 쿠키에 세션 ID를 넣고 서버가 상태를 보관합니다. HTTP 연결 유지와 로그인 세션 유지는 다른 개념입니다.

REFERENCE 11

대역폭·처리량·지연 시간

지표 뜻 예
대역폭 연결이 제공하는 전송 용량 100 Mbps 회선
처리량 실제로 전달되는 데이터 양/시간 초당 8 MB 다운로드
지연 시간 데이터·요청이 도착하거나 완료되기까지의 시간 요청 응답 100 ms
RTT 갔다가 돌아오는 왕복 시간 연결 협상 비용에 영향
지터 지연 시간의 변동 음성·영상 끊김에 영향
패킷 손실 전달 도중 사라지는 비율 재전송·품질 저하 발생

1 byte = 8 bits입니다. 100 Mbps는 이론상 12.5 MB/s이고, 100 MB 전송에는 최소 약 8초가 듭니다(십진 단위, 부가 비용 제외). 프로토콜 헤더·경합·서버·디스크·손실 때문에 실제 시간은 더 길 수 있습니다. 회선 대역폭을 늘려도 DB 쿼리가 3초 걸리는 병목이 자동으로 사라지지는 않습니다.

라우팅 테이블 목적지별 다음 경로 설정
Internet Gateway VPC의 인터넷 연결 경로 구성
Security Group 연결 상태를 추적하는 자원 수준의 허용 규칙
Network ACL 서브넷 수준의 상태 비추적 허용·거부 규칙
NAT Gateway 일반적인 구성에서 프라이빗 자원의 외부 연결 지원

인터넷 게이트웨이로 향하는 직접 경로가 있는 서브넷을 퍼블릭 서브넷이라고 합니다. 그래도 EC2에 직접 IPv4 인터넷 접속을 하려면 공인 IPv4·보안 규칙·서비스 수신 설정 등이 필요합니다. 프라이빗 서브넷도 NAT 등의 경로가 있으면 외부로 요청할 수 있습니다.

Security Group은 허용된 연결의 응답을 상태에 따라 허용합니다. NACL은 상태를 추적하지 않으므로 응답 방향의 규칙과 임시 포트도 고려합니다. 애플리케이션 인증·권한 검사까지 대체하지는 않습니다.

내 PC에서 요청과 응답 관찰하기

새 실습 폴더에 공개해도 되는 예제 파일 하나만 만들고 루프백으로 서버를 실행합니다. 아래 명령은 macOS/Linux 기준입니다. 8090번을 이미 쓰면 다른 빈 포트로 바꾸세요.

bash
mkdir -p network-basics-lab
cd network-basics-lab
printf '<h1>Hello network</h1>\n' > index.html
python3 -m http.server 8090 --bind 127.0.0.1

다른 터미널에서 요청합니다. 첫 요청은 200, 없는 경로는 404를 관찰합니다. 서버 터미널의 로그도 확인한 뒤 Ctrl+C로 종료합니다.

bash
curl -i http://127.0.0.1:8090/
curl -i http://127.0.0.1:8090/missing

브라우저에서도 http://127.0.0.1:8090/를 열고 개발자 도구의 Network 탭에서 상태·헤더·응답·시간을 봅니다. 외부 네트워크를 확인할 때는 아래처럼 DNS와 HTTP를 따로 관찰할 수 있습니다(인터넷 필요).

bash
dig example.com A
curl -I https://example.com

Windows PowerShell에서는 Resolve-DnsName example.com, HTTP 확인은 curl.exe -I https://example.com을 사용할 수 있습니다.

REFERENCE 16

복습: 한 번의 웹 요청 설명하기

“도메인으로 IP를 찾고, 경로와 포트를 통해 연결한 뒤, 암호화된 HTTP 요청을 서버 프로그램에 전달한다. 서버가 계산하거나 DB를 기다리고 응답한다.” 이 흐름에서 주소·전송·애플리케이션을 구분해 보세요.

  • IP를 알면 항상 접속 가능한가? → 경로·포트·방화벽·서비스 상태도 맞아야 합니다.
  • 100 Mbps는 100 MB/s인가? → 아닙니다. 이론상 12.5 MB/s입니다.
  • HTTPS는 항상 TCP인가? → HTTP/3는 QUIC/UDP 기반입니다.
  • 서버의 스레드를 늘리면 네트워크가 빨라지는가? → 대기 동시 처리에는 도움이 될 수 있지만 회선·DB·CPU 병목은 따로 확인합니다.
