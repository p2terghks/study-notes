02. value(x)와 라벨 검사

누락 값과 잘못된 라벨을 먼저 확인

value(x)는 필드 값 하나를 받아 문자열 하나를 돌려줍니다. x가 NULL이거나 길이가 1이 아니면 빈 문자열을 즉시 반환합니다. 예: value(NULL) → "", value("GetObject") → "GetObject". 길이 1인 NA를 빈칸으로 바꾸는 함수는 아닙니다. valid_label의 익명함수는 이벤트 하나 e를 받아 should_sample이 논리형·길이 1·NA 아님을 모두 만족하는지 검사합니다. &&는 왼쪽 조건이 거짓이면 오른쪽을 검사하지 않습니다. vapply()는 논리값 하나씩을 모아 4,216개짜리 벡터를 만듭니다. 하나라도 잘못되면 stop()으로 중단하여 누락 라벨을 일반 활동으로 오인하지 않게 합니다.

반복은 어디서 일어날까요?

vapply()는 이벤트 4,216개를 각각 처리합니다. API 그래프의 바깥 for는 선택 API 6개를, 안쪽 for는 일반·공격 두 집단을 반복하므로 막대 자리 12개를 계산합니다. 전체 구성 그래프는 두 범주, 공격 유형 그래프는 세 범주를 반복합니다. 마지막 두 kind 반복은 파일용 그래프 3종과 화면용 그래프 3종입니다. 화면용 반복은 interactive()가 참일 때만 실행됩니다.

데이터가 바뀌는 모습

아래 JSON은 구조를 설명하기 위해 줄인 예시입니다. 실제 원본 전체를 대체하는 입력은 아닙니다.

{"Records": [
  {"eventName": "GetObject", "eventSource": "s3.amazonaws.com",
   "should_sample": true, "attack_name": "MassGetMultipleBuckets"}
]}
events: 이벤트 목록→e: 이번 이벤트 한 개→e$should_sample: TRUE→group: 공격→tab의 GetObject/공격 칸 +1

실제 데이터의 공격 GetObject는 466건입니다. 공격 전체 541건으로 나눠 86.14%를 얻습니다. 이 수치는 “GetObject 중 공격일 확률”이 아니라 “공격 기록 중 GetObject가 차지하는 비율”입니다.

원본을 바로 세면 왜 불편할까요?

JSON은 이벤트마다 중첩 목록을 꺼내야 합니다. records라는 표로 바꾸면 각 이벤트를 한 행으로 맞추고 group·event·service 열을 사용해 쉽게 집계할 수 있습니다. 이 변환은 분석용 표 정리이며 데이터베이스의 정규화 설계를 뜻하지는 않습니다.

발표용 설명과 예상 질문

“이 프로젝트는 공개 AWS CloudTrail 기록 4,216건을 일반 활동과 공격으로 구분해 API 사용 패턴을 비교했습니다. 집단 크기가 다르기 때문에 건수뿐 아니라 각 집단 내부 비율을 계산했습니다. 일반 활동에서는 업로드, 공격에서는 다운로드 API의 비중이 높았습니다. 다만 기존 라벨을 비교한 결과이며 API 이름 하나로 공격 여부를 단정하지는 않습니다.”

왜 실패 기록을 공격으로 분류하지 않나요?

일반 사용자의 실수도 실패할 수 있고, 공격자의 작업도 성공할 수 있습니다. 이 분석은 요청 결과가 아니라 제작자의 should_sample 라벨을 사용합니다.

왜 541건을 기준으로 나누나요?

공격 집단에서 어떤 행동이 많이 발생하는지 비교하려는 목적이기 때문입니다. 일반 활동은 3,675건, 공격은 541건을 분모로 사용합니다.

공격을 자동으로 탐지했나요?

아닙니다. 이미 라벨이 있는 데이터를 설명·비교하는 분석입니다. 새로운 기록을 분류하는 모델의 성능은 평가하지 않았습니다.

데이터를 줄이거나 공격 비율을 맞췄나요?

아닙니다. 원본 4,216건을 모두 사용했습니다. 그래프만 각 집단 상위 4개 API의 합집합을 보여주며 전체 API 집계는 CSV에 저장합니다. 중복 eventID 수는 따로 기록하지만 행을 제거하지 않습니다.
