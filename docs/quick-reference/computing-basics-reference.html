REFERENCE 01

컴퓨터가 프로그램을 실행하는 흐름

저장장치에 있는 프로그램을 메모리에 준비하고, CPU가 명령을 실행합니다. 운영체제는 CPU 시간·메모리·파일·장치 접근을 관리합니다.

text
SSD/HDD: 프로그램과 파일을 오래 보관
   ↕ 필요한 데이터 읽기·쓰기
RAM: 실행 중인 코드와 데이터를 보관
   ↕ 캐시를 거쳐 데이터 접근
CPU: 명령 실행·계산·분기
   ↕ 운영체제를 통해 입출력 요청
디스크 / 네트워크 / 화면 등

모든 파일을 한 번에 RAM에 올리는 것은 아닙니다. 필요한 페이지를 가져오거나 파일을 매핑할 수 있습니다. 서버도 같은 원리로 실행되는 컴퓨터이며, 네트워크를 통해 다른 프로그램의 요청을 받습니다.

REFERENCE 02

CPU · 소켓 · 코어 · 논리 프로세서

용어 의미 비유
CPU 명령을 실행하는 프로세서 일을 처리하는 작업장
소켓 물리 프로세서 패키지를 장착하는 자리 작업장을 설치하는 자리
물리 코어 CPU 내부의 실행 자원을 가진 처리 단위 실제 작업자
논리 프로세서 OS가 작업을 배정할 수 있는 하드웨어 실행 문맥 작업을 배정할 수 있는 자리
클럭 일정 시간 동안의 동작 주기 수 작업 박자

CPU 패키지 하나에 여러 코어가 들어갈 수 있습니다. SMT를 지원하면 물리 코어 하나가 여러 논리 프로세서로 보일 수 있습니다. 단, 논리 프로세서들이 실행 자원을 공유하므로 물리 코어를 그만큼 추가한 것과 같지는 않습니다. Intel: 코어·vCPU·하이퍼스레딩

REFERENCE 03

가장 중요한 차이 — 코어와 스레드

코어는 하드웨어, 프로그램의 스레드는 실행할 작업 흐름입니다. 다만 제품 사양에서 ‘스레드’라는 말은 하드웨어 스레드/논리 프로세서를 뜻하기도 합니다.

구분 무엇을 세는가? 예
물리 코어 수 하드웨어의 코어 4코어 CPU
CPU 사양의 스레드 수 OS에 보이는 하드웨어 실행 문맥 SMT가 있는 4코어 8스레드
프로그램의 스레드 수 소프트웨어의 실행 흐름 웹 서버가 만든 스레드 100개
text
예: 모든 코어가 2-way SMT를 지원하는 CPU
물리 코어 0 → 논리 프로세서 0, 1
물리 코어 1 → 논리 프로세서 2, 3
물리 코어 2 → 논리 프로세서 4, 5
물리 코어 3 → 논리 프로세서 6, 7
                  ↑
OS가 실행 가능한 소프트웨어 스레드를 배정

4코어 8스레드 CPU에서 프로그램 스레드 100개를 만들 수도 있습니다. 100개가 모두 동시에 CPU를 쓰는 것은 아니며, 일부는 실행되고 일부는 차례나 입출력을 기다립니다. 스레드는 실행 중 다른 코어로 이동할 수도 있습니다. ‘8스레드 CPU에는 프로그램 스레드 8개만 만들 수 있다’는 뜻이 아닙니다.

모든 CPU가 코어 수의 두 배만큼 논리 프로세서를 제공하지는 않습니다. SMT 없는 코어, 성능 코어·효율 코어가 섞인 구성도 있습니다. Intel: Hyper-Threading

REFERENCE 04

프로그램 · 프로세스 · 스레드

용어 설명 비유
프로그램 저장된 코드와 실행 파일 요리법
프로세스 실행 중인 프로그램의 자원·주소 공간 등을 묶은 단위 운영 중인 주방
스레드 프로세스 안에서 코드를 실행하는 흐름 주방 안의 작업 흐름
text
프로세스 A: 웹 서버
  ├─ 스레드 1: 요청 처리
  ├─ 스레드 2: 요청 처리
  └─ 공유: 코드·힙·열린 파일 등
프로세스 B: 별도 프로그램
  └─ 기본적으로 별도의 가상 주소 공간

같은 프로세스의 스레드는 주소 공간과 많은 자원을 공유하지만 각자 실행 위치·레지스터 상태·스택 등을 갖습니다. 프로세스 사이에는 기본적인 메모리 격리가 있으며, 통신에는 소켓·파이프·공유 메모리 같은 방법을 사용합니다. 공유 메모리를 명시적으로 사용하는 예외도 있으므로 ‘프로세스끼리는 절대 메모리를 공유할 수 없다’고 외우지 않습니다.

REFERENCE 05

동시성 · 병렬성 · 멀티태스킹

동시성은 여러 작업을 진행 중인 상태로 다루는 것, 병렬성은 같은 순간에 여러 작업을 실제로 실행하는 것입니다.

text
시간 →
한 실행 자리를 번갈아 사용: A A | B B | A A | B B   (동시성)
서로 다른 코어에서 실행:
  코어 1: A A A A
  코어 2: B B B B                                 (병렬성)

싱글 코어에서도 작업 전환으로 여러 프로그램을 동시에 사용하는 것처럼 보이게 할 수 있습니다. 멀티코어는 작업이 나눠질 수 있을 때 실제 병렬 실행을 돕습니다. 처리 순서가 서로 의존하거나 공유 자원에서 막히면 코어를 늘려도 효과가 작을 수 있습니다.

REFERENCE 06

스케줄링 · 문맥 교환 · 상태

운영체제의 스케줄러는 실행 가능한 OS 스레드 등에 CPU 시간을 배정합니다. 실행 대상을 바꿀 때 필요한 문맥을 저장하고 복원하는 것을 **문맥 교환(context switch)**이라고 합니다.

상태 의미 CPU가 많으면 해결될까?
실행 중 CPU에서 명령 처리 작업을 나눌 수 있는지 확인
실행 대기 실행할 수 있지만 CPU 차례 대기 CPU 용량이 영향을 줄 수 있음
대기/블로킹 네트워크·디스크·락 등 기다림 기다리는 원인을 먼저 확인

문맥 교환에는 비용이 있고 캐시 효율도 영향을 받을 수 있습니다. 스레드를 무조건 많이 만들면 처리량이 늘기보다 메모리·전환·경쟁 비용이 늘 수 있습니다. 정확한 상태 이름과 스케줄링 정책은 운영체제마다 다릅니다.

REFERENCE 07

CPU bound · I/O bound · 스레드 풀

구분 주로 걸리는 시간 예 먼저 검토할 개선
CPU bound 계산 영상 인코딩·큰 수치 계산 알고리즘·벡터화·실제 병렬 처리
I/O bound 외부 응답 대기 DB 조회·파일·HTTP 요청 쿼리·캐시·비동기·적절한 동시 요청

스레드 풀은 작업마다 스레드를 새로 만들기보다 일정 수의 작업자를 재사용합니다. 풀이 너무 작으면 대기열이 길어지고, 너무 크면 메모리·문맥 교환·DB 연결 경쟁이 커집니다. 적절한 크기는 실제 작업의 CPU/대기 비율과 하위 시스템 한계로 결정합니다.

웹 요청 1,000개가 연결되어 있어도 모두 동시에 CPU를 사용하는 것은 아닙니다. 반대로 CPU 작업을 스레드 1,000개로 쪼갠다고 물리 처리 능력이 1,000배 늘어나지 않습니다.

REFERENCE 08

동기 · 비동기와 블로킹 · 논블로킹

입문에서는 작업 완료를 어떻게 받는가와 호출한 실행 흐름이 기다리는가를 나눠 생각하면 도움이 됩니다. 용어의 세부 의미는 API 문맥에 따라 달라질 수 있습니다.

표현 살펴볼 질문 예
동기 현재 흐름에서 완료·결과를 받아 다음으로 가는가? 파일 읽기 결과를 받은 뒤 계산
비동기 완료를 나중에 콜백·이벤트·Future 등으로 받는가? 요청 제출 후 완료 알림 처리
블로킹 호출 중 현재 스레드가 진행하지 못하고 기다리는가? 데이터가 올 때까지 read 대기
논블로킹 지금 처리할 수 없으면 즉시 돌아오는가? 준비 안 됨을 반환하고 다음 작업

비동기 API가 반드시 새 스레드를 만들지는 않습니다. 이벤트 루프는 한 흐름에서도 여러 I/O 대기를 관리할 수 있습니다. await로 코루틴이 멈추더라도 OS 스레드 전체가 같은 방식으로 멈춘다고 단정하지 않습니다. 비동기와 멀티스레드는 같은 말이 아닙니다.

REFERENCE 09

공유 데이터 · 경쟁 상태 · 락 · 교착 상태

여러 실행 흐름이 같은 데이터를 수정할 때 결과가 실행 순서에 따라 달라질 수 있습니다.

text
초기 count = 0
A: count를 읽음 → 0
B: count를 읽음 → 0
A: 1을 저장
B: 1을 저장
최종 count = 1  (두 번 증가했지만 2가 아님)

읽기·계산·쓰기가 하나의 원자적 연산으로 보호되지 않은 상황의 예입니다. 락(mutex), 원자적 연산, 메시지 전달 등으로 필요한 불변 조건을 지킵니다. 락은 정확성을 위해 사용하며 무조건 속도를 높이는 도구가 아닙니다.

  • 경쟁 상태: 타이밍 때문에 결과가 달라짐.
  • 교착 상태(deadlock): A는 B가 가진 자원을, B는 A가 가진 자원을 기다려 서로 진행하지 못함.
  • 기아(starvation): 특정 작업이 계속 차례를 받지 못함.

락을 잡는 순서를 통일하고, 잠근 상태에서 긴 네트워크 호출을 피하는 등 대기 구조를 설계해야 합니다.

REFERENCE 10

RAM · 캐시 · SSD · 가상 메모리

구분 역할 기억할 점
CPU 캐시 자주 필요한 데이터를 CPU 가까이에 보관 작고 빠름, 코어별/공유 구성이 다름
RAM 실행 중인 작업 공간 일반적인 RAM은 전원 종료 시 내용 소실
SSD/HDD 파일·데이터를 지속 보관 RAM과 속도·접근 방식이 다름
가상 메모리 프로그램에 주소 공간을 제공하고 실제 저장 위치에 매핑 RAM+스왑을 단순 합친 뜻이 아님
스왑 일부 메모리 내용을 저장장치로 이동 RAM과 같은 속도를 제공하지 않음

페이지 폴트는 필요한 페이지 매핑/접근을 운영체제가 처리해야 하는 상황입니다. 모든 페이지 폴트가 디스크 읽기나 오류를 뜻하지는 않습니다. 메모리가 부족해 과도하게 스왑하면 CPU가 남아도 시스템이 느려질 수 있습니다. Linux 메모리 개념

프로세스의 가상 메모리 크기와 실제 RAM 점유는 같지 않습니다. 공유 메모리·파일 캐시까지 고려해야 하므로 프로세스별 숫자를 단순 합산해 전체 사용량이라고 단정하지 않습니다.

REFERENCE 11

클럭 · 사용률 · 처리량을 읽는 법

GHz는 처리 능력의 한 요소이며 서로 다른 CPU를 숫자 하나로 비교할 수는 없습니다. 3 GHz는 초당 약 30억 주기라는 뜻이지 모든 프로그램이 초당 30억 명령을 처리한다는 뜻은 아닙니다.

지표 의미 주의
CPU 사용률 측정 구간에서 CPU가 사용된 정도 전체 기준인지 논리 CPU 하나 기준인지 확인
처리량 단위 시간에 완료한 작업 수 초당 요청 수(RPS) 등
지연시간 작업 하나에 걸리는 시간 평균뿐 아니라 p95·p99 확인
대기열 처리 차례를 기다리는 작업 CPU·DB 풀·네트워크 등 원인 구분

도구에 따라 프로세스 CPU 100%가 논리 CPU 하나를 가득 쓰는 뜻이고, 여러 CPU를 쓰면 100%를 넘기도 합니다. 다른 도구는 전체를 100%로 정규화합니다. p95=200ms라면 관찰한 요청 약 95%가 200ms 이하였다는 뜻이지 모든 요청이 그 안에 끝났다는 뜻은 아닙니다.

전체 시간이 10초이며 이 중 반드시 순서대로 실행할 부분이 5초라면, 나머지 5초를 5배 빠르게 해도 총 6초입니다. 코어를 늘릴 때 순차 구간과 통신·동기화 비용을 함께 봅니다.

vCPU · 가상 머신 · 컨테이너

용어 의미 코어와의 관계
vCPU 가상 머신 등에 제공하는 CPU 실행 자원 물리 코어/하드웨어 스레드 매핑이 환경마다 다름
VM 가상 하드웨어 위에 게스트 OS를 실행 하이퍼바이저가 자원을 관리
컨테이너 프로세스를 격리하고 자원 사용을 제한하는 실행 방식 코어를 새로 만드는 기술이 아님

예를 들어 SMT를 사용하는 일부 EC2에서는 물리 코어 2개×코어당 2스레드가 4 vCPU로 표시됩니다. 그러나 모든 인스턴스의 1 vCPU를 ‘물리 코어 반 개’라고 계산하면 틀립니다. 인스턴스 종류와 CPU 옵션을 확인하세요. AWS EC2 CPU 옵션

Linux 컨테이너는 보통 호스트 Linux 커널을 공유합니다. macOS의 Docker Desktop은 Linux VM을 거쳐 Linux 컨테이너를 실행하므로 Mac 커널을 그대로 공유하는 것은 아닙니다. CPU 제한·할당량은 사용 가능한 CPU 시간을 제한할 수 있으며 전용 물리 코어 예약과 항상 같은 의미는 아닙니다.

REFERENCE 13

언어의 스레드와 OS 스레드가 항상 같을까?

런타임이 많은 작업 흐름을 적은 OS 스레드에 배정하기도 합니다. 따라서 ‘소프트웨어 스레드 수 = OS 스레드 수 = 코어 수’라는 공식은 성립하지 않습니다.

  • Java 플랫폼 스레드: 일반적으로 OS 스레드와 연결됩니다.
  • Java 가상 스레드: 런타임이 많은 가상 스레드를 OS 스레드에 배정합니다. 대기 작업을 많이 처리하는 데 유리할 수 있지만 CPU 계산 자체를 더 빠르게 만드는 것은 아닙니다.
  • Python: 기본 GIL이 있는 CPython에서는 순수 Python CPU 작업이 일반 스레드만으로 여러 코어에서 병렬 실행되지 않는 경우가 많습니다. I/O 대기에는 스레드가 유용하며, GIL을 해제하는 확장이나 free-threaded 빌드는 조건이 다릅니다.
