서버와 클라이언트 함수 흐름

서버 동작 순서
  1. 소켓 생성: socket()
  2. 소켓에 인터넷 주소 부여: bind()
  3. 연결 요청 대기: listen()
  4. 연결 수락: accept()
  5. 데이터 읽기: read()
  6. 데이터 쓰기: write()
  7. 다시 대기로 돌아감 (슬라이드는 3번)
클라이언트 동작 순서
  1. 소켓 생성: socket()
  2. 서버에 연결: connect()
  3. 데이터 쓰기: write()
  4. 데이터 읽기: read()
  5. 연결 종료: close()

서버는 bind로 주소를 직접 지정하지만, 클라이언트는 connect 때 OS가 자동으로 IP/포트를 붙여 줍니다.

점검문제: 서버/클라이언트 함수의 동작 순서와 상호 관련성 (모범 답안) 서버는 socket → bind → listen → accept → read/write 순서, 클라이언트는 socket → connect → write/read → close 순서로 동작한다. 클라이언트의 connect가 서버의 listen 대기 큐로 연결 요청을 보내고, 서버의 accept가 이를 수락하여 연결이 성립한다. 이후 클라이언트의 write(데이터 요청)는 서버의 read와, 서버의 write(응답)는 클라이언트의 read와 짝을 이룬다.

IPv4 소켓 주소 구조체

struct sockaddr_in {
    sa_family_t    sin_family;   /* 주소 체계 (AF_INET) */
    uint16_t       sin_port;     /* 포트 번호 (16 bits)  NBO */
    struct in_addr sin_addr;     /* IP 주소 (32 bits)    NBO */
    char           sin_zero[8];  /* 16바이트 크기를 맞추기 위한 dummy */
};
struct in_addr {
    uint32_t       s_addr;       /* 32비트 IP 주소 */
};
필드크기설명
sin_family2 byte주소 체계. IPv4는 AF_INET
sin_port2 byte포트 번호. 네트워크 바이트 순서(NBO) 필수 → htons()
sin_addr4 byteIP 주소. NBO 필수 → htonl(), inet_addr()
sin_zero8 bytedummy. memset()/bzero()로 모두 0으로 채워야 함
데이터 유형 (POSIX)설명
sa_family_tunsigned short int
uint16_tunsigned 16-bit 정수
uint32_tunsigned 32-bit 정수
sockaddr vs sockaddr_in 둘 다 크기는 16 byte로 같습니다. 범용 구조체 sockaddr은 sa_family(2) + sa_data(14)이고, IPv4용 sockaddr_in은 sin_family(2) + sin_port(2) + sin_addr(4) + sin_zero(8)입니다. 소켓 함수(bind, connect, accept 등)가 struct sockaddr *을 요구하므로, 보통 sockaddr_in에 값을 채운 뒤 (struct sockaddr *)&addr로 캐스팅해서 넘깁니다.

  • Big-endian: 상위 바이트가 낮은 번지에 먼저 저장 (사람이 숫자를 쓰는 순서와 같음)
  • Little-endian: 하위 바이트가 낮은 번지에 먼저 저장
  • 호스트 바이트 순서(HBO): 내 CPU의 저장 방식 / 네트워크 바이트 순서(NBO): Big-endian으로 약속
왜 필요한가? (불일치 문제) Big-endian 컴퓨터가 0x1234를 12 34 순서로 보내면, Little-endian 컴퓨터는 앞 바이트를 하위로 읽어 0x3412로 해석합니다. 해결책은 송수신 때 항상 네트워크 바이트 순서(Big-endian)로 통일하는 것입니다.
htons / ntohs / htonl / ntohl바이트 순서 변환
u_short htons(u_short host_short); // 호스트 → 네트워크, 16bit (포트) u_short ntohs(u_short network_short); // 네트워크 → 호스트, 16bit u_long htonl(u_long host_long); // 호스트 → 네트워크, 32bit (IP 주소) u_long ntohl(u_long network_long); // 네트워크 → 호스트, 32bit
이름 읽는 법host, network, short(16bit), long(32bit). htons = host to network short
반환값변환된 값. Big-endian 컴퓨터에서는 변환해도 값이 그대로(아무 일도 안 함)
주의바이트 순서를 맞춰야 하는 것은 포트 번호, IP 주소, 정수 같은 숫자 값입니다. 텍스트 문서, binary 파일 같은 일반 사용자 데이터는 변환할 필요 없음 (바이트 단위로 보내므로 순서가 바뀌지 않음).
// endian_conv.c
unsigned short host_port = 0x1234;
unsigned short net_port  = htons(host_port);
unsigned long  host_addr = 0x12345678;
unsigned long  net_addr  = htonl(host_addr);
printf("Host ordered port : %#x \n", host_port);    // 0x1234
printf("Network ordered port : %#x \n", net_port);  // 0x3412   (Little-endian PC)
printf("Host ordered address : %#lx \n", host_addr);   // 0x12345678
printf("Network ordered address : %#lx \n", net_addr); // 0x78563412

Little-endian PC에서 실행한 결과입니다. 바이트가 뒤집혀 보이는 이유는, 메모리의 Big-endian 배치를 숫자로 다시 읽었기 때문입니다.

점검문제: Big-endian에서 4바이트 정수 12를 Little-endian으로 전송 (모범 답안) Big-endian 메모리 배치는 00 00 00 0C입니다. 송신 측이 htonl(12)를 호출하면 Big-endian 컴퓨터에서는 변환이 없어 그대로 00 00 00 0C가 전송됩니다 (네트워크 순서 = Big-endian). Little-endian 수신 측은 받은 값에 ntohl()을 적용해 0C 00 00 00 배치(= 값 12)로 뒤집어 저장하므로 12를 올바르게 얻습니다. 변환하지 않으면 그대로 읽어 0x0C000000(= 201,326,592)이 됩니다.

점검문제: 주소 할당이 필요한 이유와 함수 (모범 답안) 소켓은 생성만 해서는 어떤 IP/포트로 데이터를 받을지 정해지지 않았기 때문에, 클라이언트가 서버를 찾아올 수 있도록 서버 소켓에 고정된 주소(IP, 포트)를 부여해야 한다. 이를 위해 호출하는 함수가 bind()이다.

bind(sockfd, (struct sockaddr *)&my_addr, sizeof(struct sockaddr));

sin_size = sizeof(struct sockaddr_in);

htonl/ntohl은 uint32_t를 받고 돌려주므로 (int), (uint32_t) 캐스팅이 들어갑니다.

Ex.3 char형 버퍼 + 바이트 순서 고려

클라이언트 (BUF_SIZE 8) 
char buf[8];
*(uint32_t *)&buf[0] = htonl(operand1);  // 앞 4바이트
*(uint32_t *)&buf[4] = htonl(operand2);  // 뒤 4바이트
write(sd, buf, 8);
read(sd, &result, 4);
서버 
char buf[8];
read(clnt_sd, buf, 8);
operand1 = (int)ntohl(*(uint32_t *)&buf[0]);
operand2 = (int)ntohl(*(uint32_t *)&buf[4]);
result = operand1 + operand2;
write(clnt_sd, &result, 4);

char 배열은 바이트 단위이므로, &buf[0], &buf[4] 위치를 uint32_t *로 해석(캐스팅)해서 4바이트씩 정수를 넣고 꺼냅니다. 이런 방식은 프로토콜 헤더처럼 바이트 배열 안에 여러 필드를 배치할 때 쓰는 기본기입니다.

슬라이드 코드에서 더 챙길 점 ① 결과값 result는 변환 없이 전송되므로, 엄밀히는 서버에서 htonl(result)로 보내고 클라이언트에서 ntohl로 받아야 엔디안이 다른 환경에서도 안전합니다.
② TCP는 경계가 없어서 read(…, 8)이 8바이트보다 적게 반환될 수 있으니, 실무에서는 반환값을 보고 8바이트가 찰 때까지 반복해서 읽습니다.
③ char 배열을 uint32_t *로 캐스팅하면 정렬(alignment) 문제나 strict aliasing 문제가 생길 수 있어서 실무에서는 memcpy를 권장합니다. (슬라이드 코드는 학습용으로 단순화)

참고: 포인터 캐스팅 (1)

int a = 3;
*&a = 4;                        // &a 로 주소를 구하고 * 로 값에 접근 → a = 4
printf("%d\n", a);               // 4
*(float *)&a = 3.1f;            // a의 메모리를 float 으로 '해석'해서 3.1f 를 기록
printf("%d\n", a);               // 1078355558  (같은 비트를 int로 읽은 값)
printf("%f\n", *(float *)&a);    // 3.100000    (같은 비트를 float로 읽은 값)

핵심: 메모리의 비트는 그대로이고, 어떤 타입으로 해석하느냐에 따라 값이 다르게 보입니다.
3.1f의 이진수는 11.00011001100110011…₂이고, 부동소수점(IEEE 754) 표현은 부호 0 | 지수 10000000 | 가수 10001100110011001100110 = 0x40466666 = 정수 1078355558입니다.

참고: 포인터 캐스팅 (2) — char 버퍼에 다양한 타입 넣기

  • &buf[0] == buf (배열 이름은 첫 원소의 주소)
  • *&buf[0] == buf[0], *buf == buf[0]
  • buf+1 == &buf[1] ... buf+7 == &buf[7]
char buf[8];
buf[0] = 'A';                       printf("%c\n",  buf[0]);               // A
buf[0] = 200;                       printf("%d\n",  buf[0]);               // -56  (signed char: 200-256)
*(int *)&buf[0] = 200;              printf("%d\n",  *(int *)&buf[0]);      // 200
*(float *)&buf[0] = 3.1f;           printf("%f\n",  *(float *)&buf[0]);    // 3.100000
*(double *)&buf[0] = 3.1;           printf("%lf\n", *(double *)&buf[0]);   // 3.100000

같은 8바이트 버퍼에 char(1바이트), int(4), float(4), double(8)을 번갈아 써 보는 예제이고, char buf[8]이 최대 double 하나를 담을 수 있는 크기입니다.

전송 데이터의 경계 (Boundary)

TCP: 경계가 없다 (바이트 스트림)
  • write/send를 호출한 횟수와 read/recv 호출 횟수가 일치하지 않아도 됨
  • write 1번이 항상 패킷 1개가 되는 것은 아님. 예: 서버가 MSG1, MSG2를 두 번 보냈는데 클라이언트가 한 번에 MSG1+MSG2를 받을 수 있음
  • 흐름제어(Flow control, 슬라이딩 윈도우): 수신 버퍼가 받을 수 있는 크기 이상은 전송하지 않음
  • 예제: tcp_server_noboundary.c / tcp_client_noboundary.c
UDP: 경계가 있다 (데이터그램)
  • sendto 1번 = 데이터그램 1개, recvfrom 1번이 정확히 그 1개를 받음 → 송수신 함수 호출 횟수가 반드시 일치해야 함
  • MSG1, MSG2, MSG3을 세 번에 걸쳐 보내면 세 번에 걸쳐 받음
  • TCP와 달리 송신 버퍼가 없어 재전송 안 함
  • 예제: udp_server_boundary.c / udp_client_boundary.c
TCP에서 메시지 경계를 지키려면? TCP는 경계를 보장하지 않으므로, 응용 계층에서 메시지 길이를 먼저 보내거나 끝 표시(구분자)를 정해 직접 경계를 구분해야 합니다. (Report #4에서 정수 2개를 정확히 8바이트로 약속한 것도 같은 맥락)

사람은 www.kornu.ac.kr 같은 이름을 쓰고, 소켓은 IP 주소가 필요합니다. 이름과 IP를 서로 바꿔 주는 것이 Name Resolver 함수이며 DNS를 이용합니다. 헤더: <netdb.h>

gethostbyaddrIP 주소 → hostent

hostent 구조체

struct hostent {
    char  *h_name;        // 공식 이름 (Official name)
    char **h_aliases;     // 별칭 리스트 (Alias list), NULL로 끝남
    int    h_addrtype;    // 주소 타입 (예: AF_INET = 2)
    int    h_length;      // 주소 길이 (예: IPv4 = 4)
    char **h_addr_list;   // IP 주소 리스트 (in_addr 구조체들), NULL로 끝남
};
#define h_addr  h_addr_list[0]     /* 첫 번째 주소 */
필드설명
h_name호스트의 공식 이름 문자열
h_aliases별칭(alias) 문자열 배열. 마지막은 NULL
h_addrtype주소 종류. IPv4는 AF_INET(2)
h_length주소 길이. IPv4는 4
h_addr_listIP 주소들(in_addr 구조체)의 포인터 배열. 도메인 하나에 IP가 여러 개일 수 있음. 마지막은 NULL
h_addr매크로. 첫 번째 주소 = h_addr_list[0]

사용 예 (get_host_byname.c 구조)

struct hostent *host = gethostbyname("www.kornu.ac.kr");
if (host == NULL) { printf("이름 변환 실패\n"); return -1; }

printf("공식 이름 : %s\n", host->h_name);
for (int i = 0; host->h_aliases[i] != NULL; i++)
    printf("별칭 %d : %s\n", i + 1, host->h_aliases[i]);
printf("주소 타입 : %s\n", host->h_addrtype == AF_INET ? "AF_INET" : "기타");
for (int i = 0; host->h_addr_list[i] != NULL; i++)
    printf("IP %d : %s\n", i + 1, inet_ntoa(*(struct in_addr *)host->h_addr_list[i]));

// get_host_byaddr.c : IP → 이름
struct in_addr addr;
addr.s_addr = inet_addr("116.68.32.16");

프로세스란?

프로세스는 "프로그램이 실행 중인 상태"입니다. 프로그램(파일)과 프로세스(실행 중인 것)의 관계는 클래스와 객체의 관계와 비슷합니다. OS는 프로세스마다 고유 번호 PID를 줍니다.

  • 프로세스는 트리 구조: 부모 프로세스 → 자식 프로세스. 최상위는 init(PID 1)
  • 확인 명령: ps -aux(모든 프로세스), ps -ef(풀 포맷), pstree(트리), cat /proc/sys/kernel/pid_max(PID 최대값)

서버에서 쓰는 소켓 함수 (모든 방식 공통)

socket→bind→listen→accept→read / write→close
socket소켓 만들기
int socket(int domain, int type, int protocol);
domain주소 체계. 보통 AF_INET (IPv4)
type통신 방식. SOCK_STREAM = TCP, SOCK_DGRAM = UDP
protocol보통 0 (type에 맞게 자동 선택)
반환값성공: 소켓 디스크립터(0 이상의 정수)
실패: -1
비유전화기를 한 대 사는 것. 아직 번호도 없고 연결도 안 됨. 이 소켓이 서버의 접수창구(ssock, 연결 소켓)가 됩니다.
bind주소(IP/포트) 붙이기
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
sockfdsocket()이 돌려준 소켓
addr붙일 IP 주소와 포트 번호가 담긴 구조체의 주소
addrlen그 구조체의 크기 (sizeof(addr))
반환값성공: 0 / 실패: -1 (이미 사용 중인 포트 등)
비유전화기에 전화번호(포트)를 등록하는 것.
listen접속 대기 시작
int listen(int sockfd, int backlog);
sockfdbind까지 끝난 소켓
backlog접속 대기 큐의 크기 (accept 되기 전에 줄 설 수 있는 최대 인원)
반환값성공: 0 / 실패: -1
비유"이제부터 전화 받겠습니다" 하고 대기 상태로 전환.
accept접속 수락 → 새 소켓 생성
int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
sockfdlisten 중인 연결 소켓(ssock)
addr접속한 클라이언트의 주소 정보가 채워질 구조체 (필요 없으면 NULL)
addrlen구조체 크기가 담긴 변수의 주소 (호출 후 실제 크기로 갱신)
반환값성공: 이 클라이언트 전용 통신 소켓(csock)
실패: -1
핵심손님이 올 때마다 새 소켓이 하나씩 생깁니다. 접수창구(ssock)는 그대로 두고, 손님 전담 소켓(csock)을 자식 프로세스/스레드에 넘기는 것이 다중 접속 서버의 핵심입니다.
연결 요청이 없으면 이 함수에서 블로킹(멈춤) 상태로 기다립니다.
read / write / close송수신과 종료
ssize_t read (int fd, void *buf, size_t count); ssize_t write(int fd, const void *buf, size_t count); int close(int fd);
fd통신 소켓 (csock)
buf받은 데이터를 저장할 / 보낼 데이터가 있는 메모리
count최대 읽을 / 보낼 바이트 수
read 반환값양수: 실제로 읽은 바이트 수
0: 상대가 연결을 끊음(EOF)
-1: 오류
write 반환값실제로 보낸 바이트 수 / -1: 오류
참고이 수업의 에코 서버 예제처럼 read로 받은 만큼을 그대로 write로 돌려보내면 에코가 됩니다.

프로세스 복제: fork() 와 PID 함수

getpid / getppidPID 확인
pid_t getpid (void); // 내 PID pid_t getppid(void); // 부모의 PID
반환값해당 프로세스의 PID (pid_t는 정수 타입)
헤더<sys/types.h>, <unistd.h>
비유getpid = 내 주민번호, getppid = 부모님 주민번호.
fork자식 프로세스 생성 (복사)
pid_t fork(void);
인자없음
부모에게생성된 자식의 PID (양수)
자식에게0
실패 시-1 (자식이 안 만들어짐)
핵심한 번 호출했는데 리턴은 두 번 일어납니다. 부모에서 한 번, 자식에서 한 번.
호출 이후의 코드는 부모와 자식이 둘 다 실행하므로, 반환값으로 "나는 부모인가 자식인가"를 구분합니다.
코드/데이터/스택이 복사되므로 이후 변수를 바꿔도 서로 영향을 주지 않습니다.
비유나를 복사기로 복사. 복사본(자식)은 복사된 순간부터 따로 행동합니다.
pid_t pid = fork();
if (pid == 0) {
    // 자식만 실행: fork()가 0을 돌려받았으므로
} else if (pid > 0) {
    // 부모만 실행: fork()가 자식 PID를 돌려받았으므로
} else {
    // pid == -1 : fork 실패
}

자식 회수: wait() / waitpid()

wait아무 자식이나 끝나길 기다림
pid_t wait(int *status);
status자식의 종료 값이 저장될 변수의 주소. 필요 없으면 NULL
슬라이드는 status/256으로 꺼내지만, 정석은 WEXITSTATUS(status) 매크로 (종료 값이 상위 바이트에 저장되기 때문)
반환값종료된 자식의 PID / -1: 자식이 없거나 오류
동작종료된 자식이 있을 때까지 부모가 블로킹(멈춤).
자식이 이미 종료되어 있다면 바로 회수하고 리턴.
wait(&s) 는 waitpid(-1, &s, 0) 과 같음.
waitpid골라서 / 멈추지 않고 기다림
pid_t waitpid(pid_t pid, int *status, int options);
pid-1: 임의의 자식 (wait와 동일)
양수: 그 PID의 자식만 기다림
status종료 값 저장 (wait와 동일)
options0: wait처럼 블로킹
WNOHANG: 종료된 자식이 없어도 즉시 리턴 (무한 대기 방지)
반환값종료된 자식 PID
0: WNOHANG인데 종료된 자식이 아직 없음
-1: 오류
비유wait는 "누구든 퇴근할 때까지 문 앞에서 기다리기", waitpid(WNOHANG)는 "문을 슬쩍 열어보고 없으면 바로 내 일 하러 가기".

예제 child_wait.c 해설

pid = fork();
if (pid > 0) {                         // 부모
    pid = wait(&pstatus);                // 자식이 끝날 때까지 대기
    printf("종료된 자식 프로세스 : %d\n", pid);
    printf("종료 값 : %d\n", pstatus/256);   // 100 출력
} else if (pid == 0) {                  // 자식
    sleep(2);                           // 2초 뒤
    exit(100);                          // 종료 값 100을 남기고 종료
}

자식이 exit(100)으로 남긴 값 100을 부모가 wait로 받아서 출력하는 예제입니다.

좀비(Zombie) 프로세스

정의: 프로세스는 이미 종료되었는데, 종료 정보(PID, 리턴 값)가 OS의 PCB에 계속 남아 있는 상태. ps에서 <defunct>로 보입니다.
왜 생기나? 자식이 끝나면 OS는 "부모가 종료 값을 물어볼 수도 있으니" 정보를 일단 보관합니다. 부모가 wait로 가져가야 그제서야 지웁니다.
언제 사라지나? ① 부모가 wait()/waitpid()로 회수 ② 부모 프로세스가 종료될 때
비유: 퇴근한 직원의 사원증이 아직 반납되지 않아 명단에 남아 있는 상태.
자식 exit(0)→좀비 (정보만 남음)→부모 wait()→완전 소멸
서버에서 왜 문제인가? 서버(부모)는 계속 accept만 하며 돌고 있습니다. 클라이언트가 끝날 때마다 좀비가 쌓이고, PID(최대 65536, 버전에 따라 조정 가능) 같은 자원이 고갈됩니다. 슬라이드 예제 2-1(fork_server.c)을 실행하고 클라이언트만 종료한 뒤 ps -a를 보면 좀비가 보이는 이유입니다.

시그널(signal)로 좀비 자동 처리

시그널은 "시스템에 특정 상황이 생겼음을 커널이나 다른 프로세스가 알려주는 신호"입니다. 자식이 종료되면 커널이 부모에게 SIGCHLD를 보내고, 부모는 이 신호가 올 때 wait를 호출하도록 등록해 두면 됩니다.

void zombie_handler(int signo)       // SIGCHLD가 오면 자동 실행

완성 서버 코드 (예제 2-3 fork_server2.c 구조)

#include <stdio.h>
#include <unistd.h>
#include <signal.h>
#include <sys/wait.h>

void zombie_handler(int signo)
{
    while (waitpid(-1, NULL, WNOHANG) > 0);   // 끝난 자식 전부 회수
}

int main(void)
{
    int ssock, csock;
    pid_t pid;

    signal(SIGCHLD, zombie_handler);         // 좀비 방지

    ssock = socket(...);   bind(...);   listen(...);

    while (1) {
        csock = accept(ssock, ...);          // 손님 접수 → 전용 소켓 생성
        pid = fork();                        // 전담 직원 복제

        if (pid == 0) {                      // ── 자식 ──
            close(ssock);                    // 접수창구는 자식에게 불필요
            read(csock, ...);                // 손님 응대
            write(csock, ...);
            close(csock);
            exit(0);                         // 종료 → SIGCHLD 발생
        }
        else if (pid > 0) {                  // ── 부모 ──
            close(csock);                    // 손님 소켓은 자식이 담당
        }
    }
}

멀티 스레드 서버 완성 코드

void *client_handler(void *arg)
{
    int csock = *(int *)arg;
    free(arg);                                // 복사해 온 소켓 번호 메모리 해제
    char buf[1024];
    int len;
    while ((len = read(csock, buf, sizeof(buf))) > 0)
        write(csock, buf, len);               // 에코
    close(csock);                             // read가 0 → 클라이언트 종료
    return NULL;
}

int main(void)
{
    pthread_t tid;
    ssock = socket(...);   bind(...);   listen(...);

    while (1) {
        csock = accept(ssock, ...);
        int *p = malloc(sizeof(int));         // ★ csock을 스레드별로 복사
        *p = csock;                           //   (&csock을 그냥 넘기면 덮어써짐)
        pthread_create(&tid, NULL, client_handler, p);
        pthread_detach(tid);                  // 종료 시 자동 정리, join 불필요
    }
}
왜 malloc으로 복사할까? pthread_create(..., &csock)로 변수 주소를 넘기면, 스레드가 값을 읽기도 전에 main이 다음 accept 결과로 csock을 덮어쓸 수 있습니다. 그러면 두 스레드가 같은 클라이언트 소켓을 처리하게 됩니다.

4. Lecture 10 · I/O 멀티플렉싱 기반 서버

핵심 아이디어

멀티플렉싱(Multiplexing)은 "하나의 통로로 여러 신호를 섞어서 처리"한다는 뜻입니다. 서버는 프로세스/스레드 1개로 모든 소켓을 맡고, 소켓의 데이터 입출력을 이벤트로 간주해 이벤트가 발생한 소켓만 처리합니다.

동작 5단계

  1. 그룹화: 감시할 소켓들을 fd_set(비트 표)에 모음
  2. 감시: select()를 호출 → 데이터 온 소켓이 생길 때까지 대기. OS가 이벤트 발생 소켓을 표에 체크
  3. 검사: 표를 순서대로 훑으며 체크된 소켓 찾기 (FD_ISSET)
  4. 처리: 체크된 소켓에서 read로 읽고 처리
  5. 2~4 반복

※ 호출 후에는 이벤트가 없는 0번, 7번이 0으로 지워집니다. 그래서 원본 표를 복사해서 넘겨야 합니다.

fd_set 자료형과 매크로

  • fd_set = 파일(소켓) 디스크립터를 모아두는 비트 단위 배열. 기본 1,024비트(128바이트) → 최대 1,024개 관리 (FD_SETSIZE)
  • 상태 변화(이벤트) 3종류 → fd_set도 3개 변수 필요
    • 수신: 읽을 데이터가 입력 버퍼에 있는가? (readfds)
    • 전송: 출력 버퍼에 여유가 있어 보낼 수 있는가? (writefds)
    • 예외: 소켓에서 예외(Out-of-Band 메시지 등)가 발생했는가? (exceptfds)
FD_ZERO / FD_SET / FD_CLR / FD_ISSETfd_set 조작 매크로
FD_ZERO (fd_set *fdset); FD_SET (int fd, fd_set *fdset); FD_CLR (int fd, fd_set *fdset); FD_ISSET(int fd, fd_set *fdset);
FD_ZERO모든 비트를 0으로 초기화. 사용 전 반드시 1번 호출
FD_SETfd 비트를 1로 → "이 소켓을 감시 대상에 등록"
FD_CLRfd 비트를 0으로 → "감시 해제" (연결이 끊긴 소켓을 뺄 때)
FD_ISSETfd 비트가 1인지 확인 → 1(참): 이벤트 발생 / 0: 없음
select 호출 후에 "어느 소켓에 일이 생겼나" 찾는 데 사용
헤더<sys/select.h> (POSIX 1003.1-2001), 그 이전은 <sys/time.h>, <sys/types.h>, <unistd.h>

select() 함수

디스크립터 설정→검사 범위 설정→타임아웃 설정→select 호출→결과 확인
select여러 소켓을 동시에 감시
int select(int nfds, // 가장 큰 fd + 1 fd_set * readfds, // 읽기 이벤트 감시 fd_set * writefds, // 쓰기 가능 감시 fd_set * exceptfds, // 예외 감시 struct timeval * timeout); // 대기 시간 제한
nfds검사할 fd 범위. 가장 큰 fd 값 + 1. (fd는 0번부터 시작하므로 +1) 개수가 아님에 주의
readfds"읽을 데이터가 생겼는지" 감시할 fd 집합. 서버 소켓과 클라이언트 소켓을 넣음
writefds"보낼 수 있는 상태인지" 감시할 집합. 쓰지 않으면 NULL
exceptfds"예외가 생겼는지" 감시할 집합. 쓰지 않으면 NULL
timeout이벤트를 기다릴 최대 시간. NULL이면 이벤트가 생길 때까지 무한 대기
반환값 > 0이벤트가 발생한 fd의 총 개수 (어느 fd인지는 FD_ISSET으로 확인)
반환값 = 0타임아웃 (시간 안에 이벤트 없음)
반환값 = -1오류 발생
중요호출 후 fd_set은 "이벤트 발생한 fd만 1"인 상태로 바뀝니다. 원본은 copyfds = readfds; 로 복사해 보존하고, 복사본을 select에 넘기세요.

FD_ZERO(&readfds);               // ① 표를 전부 0으로 초기화
FD_SET(0, &readfds);             // ② 0, 2, 4, 7번을 감시 대상으로 등록
FD_SET(2, &readfds);
FD_SET(4, &readfds);
FD_SET(7, &readfds);

copyfds = readfds;               // ③ 원본 보존용 복사 (select가 표를 바꾸므로)

select(8, &copyfds, ...);        // ④ 가장 큰 fd(7) + 1 = 8, 반환값 2 (2번, 4번에 데이터 도착)

for (i = 0; i < 8; i++) {          // ⑤ 0~7번을 차례로 검사
    if (FD_ISSET(i, &copyfds)) { // 2번, 4번에서만 참
        /* i번 소켓 read 및 처리 */
    }
}

select 기반 다중 접속 서버 (예제 select_server.c 구조)

구현 절차 ① socket ② bind ③ listen ④ 연결 소켓(ssock)을 fd_set에 추가 ⑤ select 호출 ⑥ ssock 또는 csock에 읽을 데이터가 오면 select 반환 ⑦ FD_ISSET으로 어느 소켓인지 확인
  1) ssock에 이벤트 → accept() 후 새 통신 소켓을 fd_set에 추가
  2) csock에 이벤트 → read()로 데이터 처리
⑧ ⑤로 복귀
fd_set readfds, copyfds;
int maxfd, i, n, len;
char buf[1024];

ssock = socket(...);   bind(...);   listen(...);

FD_ZERO(&readfds);
FD_SET(ssock, &readfds);               // 접수창구도 감시 대상에 넣는다
maxfd = ssock;                         // 가장 큰 fd 번호 기억

while (1) {
    copyfds = readfds;                                   // 원본 보존
    n = select(maxfd + 1, &copyfds, NULL, NULL, NULL);   // 벨이 울릴 때까지 대기
    if (n < 0) break;

    for (i = 0; i <= maxfd; i++) {
        if (!FD_ISSET(i, &copyfds)) continue;          // 이벤트 없는 fd는 건너뜀

        if (i == ssock) {                                // ① 새 손님 도착
            csock = accept(ssock, ...);
            FD_SET(csock, &readfds);                     //    감시 대상에 추가
            if (csock > maxfd) maxfd = csock;              //    maxfd 갱신
        } else {                                         // ② 기존 손님이 데이터 전송
            len = read(i, buf, sizeof(buf));
            if (len <= 0) {                                //    0이면 상대가 연결 종료
                close(i);
                FD_CLR(i, &readfds);                     //    감시 해제
            } else {
                write(i, buf, len);                      //    에코 응답
            }
        }
    }
}
한계 직원이 한 명(단일 스레드)이라서, 어떤 클라이언트의 처리가 오래 걸리면 그동안 다른 클라이언트는 모두 대기합니다. 또한 select는 fd를 순서대로 훑으므로 수천 개 이상에서는 비효율적일 수 있습니다.

5. JavaNet 1 · I/O Stream

스트림이란?

스트림(Stream)은 순서가 있는 데이터의 연속적인 흐름입니다. 입출력 장치(키보드, 파일, 네트워크)와 프로그램 사이의 수도관이라고 생각하면 됩니다. 흘러가는 기본 단위는 바이트입니다.

  • 단방향: 입력과 출력을 동시에 하려면 스트림이 2개 필요
  • 선입선출(FIFO): 먼저 들어간 데이터가 먼저 나옴
  • 연결 가능: 관을 이어 붙이듯 연결 (예: System.in → InputStreamReader → BufferedReader)
  • 지연될 수 있음 (데이터가 올 때까지 기다림)
입력출력단위 / 용도
바이트 스트림…InputStream…OutputStream1바이트(8bit). binary 데이터(이미지, 실행 파일) 처리. 문자도 읽고 쓸 수는 있음
문자 스트림…Reader…Writer문자(Unicode). 텍스트 전용, binary는 처리 불가. 로컬 문자 집합으로 자동 변환

이름 끝만 보면 구분됩니다: ~Stream = 바이트, ~Reader/~Writer = 문자. 문자 스트림은 바이트 스트림을 감싼 wrapper입니다.

버퍼 스트림과 flush

왜 필요한가? 프로그램 속도는 빠른데 디스크/장치는 느립니다. write를 호출할 때마다 OS API가 호출되면 속도가 크게 떨어집니다.
→ 버퍼(임시 저장소)에 데이터를 모아뒀다가 한꺼번에 내보내 효율을 높입니다.
비유: 물을 한 컵씩 나르지 않고 물탱크에 모아 한 번에 옮기는 것. 읽을 때도 한 번에 큰 덩어리를 읽어 놓고 하나씩 꺼내 씁니다.
메서드 / 생성자설명

BufferedOutputStream(OutputStream out, int size)size 바이트 버퍼를 가진 출력 스트림 (기본 8192)

큰 그림 · 소켓은 창구, 패킷은 봉투

DatagramSocket
실제로 UDP를 보내고 받는 통신 창구. 서버·클라이언트 모두 같은 클래스입니다.
DatagramPacket
byte[] 데이터와 주소·포트·길이를 담는 봉투. 생성만으로 전송되지 않습니다.

UDP는 연결 설정 없이 데이터그램 단위로 통신합니다. 전달·순서·중복 방지를 보장하지 않습니다. TCP의 ServerSocket/accept와 같은 접속 수락 단계가 없으며, 필요한 신뢰성은 응용 프로그램에서 구현합니다. MulticastSocket은 여러 수신자에게 보내는 멀티캐스트용 클래스입니다.

import java.net.*;
import java.nio.charset.StandardCharsets;
public class UDPReceiver {

예제 3 · UDP Echo 서비스

에코는 받은 바이트를 그대로 돌려주는 서비스입니다. 서버는 수신 패킷의 송신자 주소·포트로 응답해야 여러 클라이언트를 상대할 수 있습니다. 아래 예제는 원문의 고정 포트 10000·루프백 응답을 일반화했습니다.

UDPEchoServer.java

import java.net.*;
public class UDPEchoServer {
    public static void main(String[] args) throws Exception {
        try (DatagramSocket socket = new DatagramSocket(20000)) {
            byte[] buf = new byte[2048];
            DatagramPacket request = new DatagramPacket(buf, buf.length);
            while (true) {
                request.setLength(buf.length); // 이전 수신 길이를 초기화
                socket.receive(request);
                DatagramPacket reply = new DatagramPacket(
                        request.getData(), request.getOffset(), request.getLength(),
                        request.getAddress(), request.getPort());
                socket.send(reply);
            }
        }
    }
}

UDPEchoClient.java

import java.net.*;
import java.nio.charset.StandardCharsets;
public class UDPEchoClient {
    public static void main(String[] args) throws Exception {
        InetAddress server = InetAddress.getByName("127.0.0.1");
        byte[] data = "UDP 소켓 프로그래밍".getBytes(StandardCharsets.UTF_8);
        try (DatagramSocket socket = new DatagramSocket()) {
            socket.connect(server, 20000); // 응답을 받을 상대 지정
            socket.setSoTimeout(3000);
            socket.send(new DatagramPacket(data, data.length, server, 20000));
            byte[] buf = new byte[2048];
            DatagramPacket reply = new DatagramPacket(buf, buf.length);
            try {
                socket.receive(reply);
                System.out.println(new String(reply.getData(), reply.getOffset(),
                        reply.getLength(), StandardCharsets.UTF_8));
            } catch (SocketTimeoutException e) {
                System.out.println("3초 안에 응답이 없습니다.");
            }
        }
    }
}
