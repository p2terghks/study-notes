트러블슈팅은 증상을 확인하고, 로그와 상태로 원인을 좁힌 뒤, 필요한 부분만 수정하고 재검증하는 과정입니다. 이 문서는 현재 프로젝트와 Terraform 예제에 맞춘 문제 해결 가이드입니다. 아래 증상이 실제 계정에서 발생했다는 뜻은 아니며, 이번 작업에서는 AWS 계정에 접속하거나 설정을 변경하지 않았습니다.

2. 진단용 환경값 준비

실행 위치: 개발 PC의 수강2 프로젝트 루트. infra/terraform은 배포 가이드에서 예제를 복사해 실제 환경에 적용한 폴더입니다. 문서 예제 폴더를 그대로 가리키면 실제 state가 없으므로 output을 읽을 수 없습니다.

export AWS_PROFILE=campus-deploy
export AWS_REGION=ap-northeast-2
export AWS_DEFAULT_REGION="$AWS_REGION"
TF_DIR=infra/terraform

aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity

프로필 이름은 본인 환경에 맞게 바꿉니다. Account·Arn이 의도한 계정인지 확인합니다. init 자체가 실패한 상태라면 output 명령으로 넘어가지 않고 4절부터 확인합니다.

# 1차 인프라 apply가 완료된 뒤에만 읽을 수 있는 값
CLUSTER=$(terraform -chdir="$TF_DIR" output -raw cluster_name)
REPOSITORY_NAME=$(terraform -chdir="$TF_DIR" output -raw repository_name)
APP_SECRET_ARN=$(terraform -chdir="$TF_DIR" output -raw app_secret_arn)
DB_HOST=$(terraform -chdir="$TF_DIR" output -raw database_endpoint)
LOG_GROUP=$(terraform -chdir="$TF_DIR" output -raw log_group)
TG_ARN=$(terraform -chdir="$TF_DIR" output -raw target_group_arn)
SITE_URL=$(terraform -chdir="$TF_DIR" output -raw site_url)

# 2차 앱 apply까지 진행해 서비스가 생성된 환경에서만 실행
SERVICE=$(terraform -chdir="$TF_DIR" output -raw service_name)

서비스 생성 도중 실패하여 service_name 출력이 아직 없으면 ECS 콘솔에서 실제 서비스 이름을 확인해 SERVICE='실제이름'으로 지정합니다. state output이 오래된 경우에도 실제 리소스가 존재하는지 함께 확인합니다. 빈 변수나 None이 보이면 뒤 명령에 그대로 넣지 않습니다.

현재 CloudFormation으로 배포한 환경에는 이 Terraform output을 쓸 수 없습니다. 그 경우 스택 Outputs와 ECS 콘솔에서 같은 의미의 값들을 확인해서 지정합니다.

3. 가장 먼저 수집할 진단 정보

다음 명령은 상태·로그를 조회합니다. API 권한이 필요하지만 서비스 설정은 바꾸지 않습니다.

aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
  --query 'services[0].{Desired:desiredCount,Running:runningCount,Pending:pendingCount,Deployments:deployments,Events:events[0:10]}'

aws ecs list-tasks --cluster "$CLUSTER" --service-name "$SERVICE" \
  --desired-status STOPPED --query 'taskArns' --output table

출력된 중지 태스크 ARN 하나를 선택합니다. 배열 순서를 최신 순으로 가정하지 않습니다. 서비스 이벤트의 시간과 연결해 보고, 여러 태스크라면 각각 stoppedAt을 비교합니다.

TASK_ARN='위에서_확인한_실제_태스크_ARN'
aws ecs describe-tasks --cluster "$CLUSTER" --tasks "$TASK_ARN" \
  --query 'tasks[].{StoppedAt:stoppedAt,StopCode:stopCode,Reason:stoppedReason,Containers:containers[].{Name:name,Exit:exitCode,Reason:reason,Image:image,ImageDigest:imageDigest}}'

aws elbv2 describe-target-health --target-group-arn "$TG_ARN"
aws logs tail "$LOG_GROUP" --since 30m --format short
curl -sS --connect-timeout 10 --max-time 20 -D - \
  "$SITE_URL/actuator/health/readiness"

stoppedReason은 태스크 전체 종료 사유, containers.reason과 exitCode는 컨테이너 상세입니다. 앱 실행 전에 실패했다면 CloudWatch 앱 로그가 없을 수 있습니다. stopped 태스크 정보는 제한된 기간 동안만 보이므로 문제 발생 직후 기록합니다. AWS 중지 태스크 진단

4. AWS 로그인·권한·Terraform init 실패

증상: ExpiredToken, InvalidClientTokenId, AccessDenied, S3 backend 접근 거부.

원인 확인: 만료된 SSO, 다른 AWS_PROFILE, 잘못된 버킷·리전, state 또는 lock 객체 권한, IAM role 전달 권한 부족을 구분합니다. AccessDenied의 Action과 Resource가 무엇인지 읽습니다.

aws sts get-caller-identity
aws configure list

STATE_BUCKET='backend.hcl의_실제_버킷명'
aws s3api head-bucket --bucket "$STATE_BUCKET"
aws s3api get-bucket-location --bucket "$STATE_BUCKET"

terraform -chdir="$TF_DIR" init -backend-config=backend.hcl

aws configure list는 값의 출처를 확인하는 용도이며 출력은 공개 게시하지 않습니다. head-bucket 성공만으로 state Put/Delete lock 권한까지 확인한 것은 아닙니다. backend에는 버킷 ListBucket, state 경로 Get/Put, .tflock 경로 Get/Put/Delete가 필요합니다.

해결: 올바른 프로필로 재로그인하고 backend의 bucket·key·region을 맞춥니다. 실제 state 위치를 바꿀 때는 -reconfigure와 -migrate-state의 목적을 구분하고 기존 state를 보존합니다. 위치를 잘못 바꾸면 리소스가 없는 새 환경으로 오인할 수 있습니다. 권한은 오류의 작업·리소스 기준으로 보완합니다.

정상 확인: init 성공 후 terraform state list에 예상 리소스가 있고 plan이 기존 리소스를 새로 만들려 하지 않는지 확인합니다. 처음 배포라 state가 빈 경우는 정상입니다. S3 backend 설정·권한

5. Terraform state 잠금 오류

증상: Error acquiring the state lock, lock ID와 소유자 정보 출력.

원인 확인: 다른 터미널·팀원·CI에서 plan/apply 중인지 확인합니다. S3 lock은 동일 state에 대한 작업을 조정합니다. 중단된 작업의 잠금인지, 실제 작업이 살아 있는지 먼저 구분해야 합니다.

해결: 실제 작업이 진행 중이면 기다립니다. 모든 실행이 종료되었고 자신이 관리하는 state에 남은 잠금임을 확인했을 때만 잠금 해제를 검토합니다. -lock=false를 반복 사용하거나 S3 파일을 임의로 지우는 방식으로 우회하지 않습니다.

# 변경 작업: 다른 실행이 없고 남은 잠금의 소유 관계를 확인한 경우에만
terraform -chdir="$TF_DIR" force-unlock 확인한_LOCK_ID

정상 확인: 정상 잠금을 사용하는 새 plan이 실행되는지 봅니다. 잠금 해제는 AWS 인프라 복구나 state 내용 복원이 아닙니다. HashiCorp force-unlock

6. plan에 삭제·교체가 나타나거나 apply가 중간에 실패

증상: -/+가 DB에 나타남, ECS가 삭제 계획에 포함됨, 이미 존재하는 이름 오류, 일부 생성 뒤 실패.

원인 확인: app_enabled=false로 되돌아갔는지, tfvars를 다른 폴더에서 읽는지, state key·workspace가 달라졌는지, 기존 리소스 블록 이름을 바꿨는지 확인합니다. immutable 속성 변경은 교체를 요구할 수 있습니다.

terraform -chdir="$TF_DIR" workspace show
terraform -chdir="$TF_DIR" state list
terraform -chdir="$TF_DIR" validate
terraform -chdir="$TF_DIR" plan

해결: 서비스 가동 후에는 app_enabled=true와 실제 image_uri를 파일에 유지합니다. Terraform 리소스 주소를 바꾸는 리팩터링에는 moved/import 등의 상태 관리가 필요할 수 있습니다. 동일 이름의 기존 CloudFormation 리소스를 새로 생성하는 것은 이관이 아닙니다.

apply가 일부 성공하고 실패하면 Terraform은 성공한 변경을 state에 기록할 수 있습니다. 먼저 실제 생성 상태와 새 plan을 확인하고 원인을 고친 뒤 재계획합니다. 이전에 저장한 오래된 plan을 무조건 다시 실행하지 않습니다. state 파일을 삭제해서 재시도하지 않습니다.

정상 확인: plan의 변경 범위가 의도한 리소스에 한정되고, DB 교체·데이터 손실을 수반하는 변경은 별도 검토 계획이 있을 때만 진행합니다.

7. 도메인이 안 열리거나 ACM 검증이 끝나지 않음

증상: DNS 조회 실패, Pending validation, 브라우저 인증서 이름 불일치.

원인 확인: 도메인 등록기관의 NS가 Route 53 public zone의 NS와 일치하는지, 인증서 검증 CNAME이 실제 권한 있는 DNS에 존재하는지 확인합니다. private hosted zone으로는 외부 도메인 검증을 해결할 수 없습니다.

DOMAIN='campus.본인도메인.com'
ZONE_DOMAIN='본인도메인.com'
dig NS "$ZONE_DOMAIN" +short
dig A "$DOMAIN" +short

# ACM이 제시한 검증 레코드 이름을 정확히 대입
dig CNAME '_실제검증이름.본인도메인.com' +short

해결: NS 위임과 CNAME의 중복 도메인 입력을 수정합니다. 예를 들어 DNS 업체가 접미사를 자동 추가하는데 전체 도메인을 다시 적으면 잘못된 이름이 됩니다. ACM 인증서는 ALB와 같은 리전에서 발급하고 해당 도메인을 포함해야 합니다. ALB 기본 DNS 이름으로 접속하면 사용자 도메인 인증서와 맞지 않을 수 있습니다.

정상 확인: 인증서 ISSUED, 도메인 A/Alias 정상, curl https://실제도메인/actuator/health/readiness에서 TLS 오류가 없음을 확인합니다. DB나 앱이 아직 없으면 HTTPS 연결 후 503이 나올 수 있으므로 TLS 성공과 앱 성공을 구분합니다. ACM DNS 검증

8. 이미지 pull 실패·아키텍처 오류

증상: CannotPullContainerError, image not found, exec format error.

원인 확인: 실제 배포 이미지 URI의 계정·리전·저장소·digest가 맞는지 확인합니다. 태그 목록에 있다는 사실만으로 현재 태스크가 그 이미지를 쓰는 것은 아닙니다.

aws ecr describe-images --repository-name "$REPOSITORY_NAME" \
  --query 'imageDetails[].{Tags:imageTags,Digest:imageDigest,PushedAt:imagePushedAt}' \
  --output table

TASK_DEF=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
  --query 'services[0].taskDefinition' --output text)
aws ecs describe-task-definition --task-definition "$TASK_DEF" \
  --query 'taskDefinition.{Platform:runtimePlatform,ExecutionRole:executionRoleArn,Containers:containerDefinitions[].{Name:name,Image:image}}'

해결: 존재하는 새 이미지 digest를 tfvars에 넣고 재배포합니다. Apple Silicon에서도 현재 예제는 docker buildx build --platform linux/amd64로 만들어야 X86_64 태스크와 맞습니다. 태그는 불변이므로 새 태그로 올립니다.

이미지가 존재하지만 연결이 시간 초과되면 private app 서브넷의 NAT 경로·NAT 상태·HTTPS egress와 Execution Role을 확인합니다. VPC endpoint를 사용하는 별도 설계라면 ECR API·DKR뿐 아니라 이미지 레이어의 S3 경로도 필요합니다.

정상 확인: 태스크가 RUNNING이 되고 describe-tasks의 실제 imageDigest가 의도한 digest와 일치합니다. 원본 이미지 다운로드/실행 단계와 Spring 부팅 단계를 구분합니다.

9. Secret 또는 로그 초기화 실패

증상: ResourceInitializationError, unable to pull secrets, failed to initialize logging driver.

원인 확인: 오류가 timeout이면 네트워크, AccessDenied면 실행 역할, 없는 ARN·버전이면 Secret 설정을 먼저 봅니다. 태스크 시작 전에는 앱 로그 자체가 없을 수 있습니다. AWS ResourceInitializationError

# 비밀번호 값 자체를 출력하지 않는 메타데이터 조회
aws secretsmanager describe-secret --secret-id "$APP_SECRET_ARN" \
  --query '{Name:Name,ARN:ARN,Versions:VersionIdsToStages,DeletedDate:DeletedDate}'

aws logs describe-log-groups --log-group-name-prefix "$LOG_GROUP" \
  --query 'logGroups[].logGroupName' --output table

해결: Secrets Manager 콘솔에서 AWSCURRENT 버전에 username·password 키가 있는지 확인합니다. 이 프로젝트의 Terraform 예제는 Secret 이름만 만들므로 값 등록이 별도로 필요합니다. 태스크 정의의 ARN 뒤에 :username::와 :password::가 맞아야 합니다. Execution Role에 해당 Secret의 GetSecretValue가 있어야 하며, 별도 고객 관리 KMS 키를 사용하면 그 키의 복호화 권한도 검토합니다.

로그 그룹의 이름·리전·존재 여부와 Execution Role의 로그 작성 권한을 확인합니다. 앱의 Task Role에 권한을 넣는 것으로 실행 에이전트 권한 문제가 자동 해결되지는 않습니다.

정상 확인: 초기화 오류 없이 새 태스크가 앱 시작 로그를 출력합니다. Secret을 수정했으면 기존 컨테이너에는 자동 적용되지 않으므로 새 태스크가 필요합니다. ECS Secret 주입

10. RDS 접속·비밀번호·스키마 권한 오류

실제 오류 의미 확인 대상
connection timed out 접속 경로가 막히거나 응답 없음 SG·서브넷·DB 주소·RDS 상태
Connection refused 대상 포트에서 연결 거부 호스트·포트·DB 상태
password authentication failed DB까지 도달했으나 인증 실패 계정 이름·Secret과 DB 비밀번호 일치
permission denied for schema public 인증됐으나 객체 생성 권한 부족 campus_app의 USAGE·CREATE
certificate / hostname verification failed TLS 검증 실패 RDS CA·엔드포인트 이름·인증서 경로

원인 확인: DB_URL이 prod용 주소인지, 앱이 campus_app을 쓰는지 확인합니다. 개인 PC에서 private RDS가 안 열린다는 것만으로 장애라고 판단하지 않습니다. VPC 관리 환경에서 확인해야 합니다.

# VPC에 접속 가능한 관리 환경에서 실행
psql "host=실제_RDS_ENDPOINT port=5432 dbname=campus user=campus_app sslmode=verify-full sslrootcert=global-bundle.pem" -W

-- 접속 후 읽기 전용 확인
SELECT current_user, current_database();
SELECT has_schema_privilege(current_user, 'public', 'USAGE') AS can_use,
       has_schema_privilege(current_user, 'public', 'CREATE') AS can_create;

해결: app SG→DB SG의 5432, RDS 상태, 올바른 엔드포인트를 확인합니다. 비밀번호 오류라면 DB 역할과 앱 Secret의 값을 일치시킵니다. 새 DB의 권한 설정은 배포 가이드 17절을 따릅니다. 기존 DB의 다른 계정 소유 테이블까지 단순 CREATE 권한으로 해결되는 것은 아닙니다.

현재 Dockerfile에는 CA가 /app/certs/global-bundle.pem에 포함되며 JDBC URL은 sslmode=verify-full을 사용합니다. 인증 오류를 피하려고 운영 TLS 검증을 끄지 않습니다.

정상 확인: 앱 계정으로 연결되고 필요한 권한이 있으며 Spring 부팅·readiness가 UP입니다. RDS PostgreSQL TLS

11. Flyway·JPA 부팅 오류

증상: migration checksum mismatch, relation already exists, missing table, schema-validation 실패.

원인 확인: prod 프로필, 접속 DB·schema, Flyway 이력을 확인합니다. 현재 프로젝트는 V1 업무 테이블, V2 공유 세션, V3 상담 프로필 순서입니다. Entity 자동 테이블 생성이 아니라 ddl-auto=validate를 사용합니다.

-- DB 관리 연결에서 읽기 전용 확인
SELECT to_regclass('public.flyway_schema_history');

-- 위 테이블이 존재하는 경우에만
SELECT installed_rank, version, description, success
FROM public.flyway_schema_history
ORDER BY installed_rank;

SELECT tablename
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY tablename;

해결: 이미 적용한 V1~V3를 수정했다면 의도치 않은 변경을 복원하고 추가 변경은 새 V4 이상으로 작성합니다. Entity만 먼저 배포하고 대응 SQL이 없으면 버전을 맞춥니다. 수동 생성 테이블과 Flyway가 충돌하면 실제 구조·소유권·이력을 비교한 이관 계획이 필요합니다.

원인 확인 없이 Flyway clean, repair, baseline, 테이블 삭제를 실행하지 않습니다. ddl-auto=update로 바꾸는 것은 현재 마이그레이션 운영 방식과 다른 스키마 변경 경로를 추가합니다.

정상 확인: 마이그레이션과 JPA 검증이 모두 통과하고 테이블이 기대 버전과 일치합니다. Flyway 성공만 확인하지 말고 readiness까지 확인합니다.

12. ALB 502·503·504와 unhealthy

원인 확인: 브라우저의 오류가 ALB에서 생성된 것인지 앱이 돌려준 것인지 구분합니다. 상태 코드 하나로 원인을 확정하지 않고 target health의 Reason·Description과 같은 시간대 앱 로그를 함께 봅니다. AWS ALB 문제 해결

aws elbv2 describe-target-health --target-group-arn "$TG_ARN" \
  --query 'TargetHealthDescriptions[].{IP:Target.Id,Port:Target.Port,State:TargetHealth.State,Reason:TargetHealth.Reason,Detail:TargetHealth.Description}'

aws elbv2 describe-target-groups --target-group-arns "$TG_ARN" \
  --query 'TargetGroups[].{Port:Port,Type:TargetType,HealthPath:HealthCheckPath,Matcher:Matcher}'
증상 흔한 확인 방향 현재 프로젝트 기준
503 등록·사용 가능한 타깃, 서비스 생성 여부 app_enabled=false 단계에는 아직 서비스 없음
502 타깃 연결 종료·잘못된 응답·앱 종료 Spring 부팅/종료 로그·8080 통신 확인
504 연결·응답 시간 초과 네트워크·느린 API·DB 대기 확인
Target.ResponseCodeMismatch 헬스 경로가 200 외 응답 readiness의 실제 상태·Security 공개 경로 확인
Target.Timeout 헬스 요청 시간 내 응답 없음 SG·8080·프로세스·DB 상태 확인

해결: target_type=ip, containerPort=8080, ALB→app SG 8080, path=/actuator/health/readiness, matcher=200을 확인합니다. 앱이 DB 때문에 부팅에 실패했다면 grace period를 늘려 숨기지 말고 DB부터 고칩니다. 모든 타깃이 unhealthy일 때의 ALB 동작도 고려해야 하므로 “unhealthy이면 무조건 503”으로 단정하지 않습니다.

정상 확인: 원하는 수의 healthy 타깃, readiness HTTP 200, 사용자 API의 정상 응답을 함께 확인합니다.

13. 로그인 반복·401·403

증상: 로그인 직후 다시 로그인 화면, 세션이 사라짐, POST만 403.

원인 확인: 브라우저 개발자 도구 Network에서 /api/login, /api/csrf, /api/state 순서를 확인합니다. 로그인 성공은 204이고 이후 state 조회가 인증 세션으로 처리되어야 합니다. 쿠키와 토큰 값 자체를 복사해 공유하지 않습니다.

결과 먼저 확인할 것
login 401 학번·비밀번호, 등록된 실제 계정
state 401 쿠키 저장·전송, 세션 만료, prod 세션 DB
login 또는 변경 요청 403 해당 세션의 최신 CSRF 토큰·헤더
태스크마다 로그인 상태가 다름 prod 설정·Spring Session JDBC 테이블
HTTP에서만 로그인 안 됨 Secure cookie이므로 HTTPS 사용

해결: 인증서 도메인의 HTTPS로 접속합니다. 현재 prod 쿠키는 Secure·HttpOnly·SameSite=Lax이고 세션은 DB로 공유합니다. V2 세션 테이블과 ProductionSessionConfig 활성화를 확인합니다. ALB 고정 세션부터 추가하여 문제를 가리지 않습니다.

프론트 getCsrf()는 토큰·헤더 이름을 받고, request()는 변경 요청에 헤더를 넣습니다. 로그인 성공 후 토큰을 다시 받는 흐름을 유지합니다. 직접 curl로 POST하면서 CSRF를 빠뜨린 경우에는 정상 보호 동작으로 403이 날 수 있습니다.

정상 확인: 로그인 → state 성공 → 새로고침 → 인증 유지 → 정상 로그아웃을 확인합니다. 새 태스크로 요청이 이동해도 공유 세션을 읽을 수 있어야 합니다.

14. 강의가 비어 있거나 수정한 화면이 안 보임

증상 A: 로그인은 되지만 강의 0개. 운영에서는 demo-enabled=false가 정상입니다. H2의 로컬 데이터를 RDS에 자동 이관하지 않습니다. 연결 대상 DB를 확인하고 강의·수업 시간 데이터를 별도 절차로 준비합니다. 이를 해결하려고 운영 체험 데이터 생성을 무작정 켜지 않습니다.

-- VPC 관리 환경의 실제 운영 대상 DB에서 개수만 확인
SELECT count(*) FROM courses;
SELECT count(*) FROM meetings;

증상 B: React를 수정했지만 이전 화면. 운영은 Vite 개발 서버가 아니라 Docker 빌드 시 JAR에 포함된 정적 파일을 사용합니다. 새 이미지 빌드·push·digest 변경·서비스 배포가 모두 필요한지 확인합니다.

TASK_DEF=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
  --query 'services[0].taskDefinition' --output text)
aws ecs describe-task-definition --task-definition "$TASK_DEF" \
  --query 'taskDefinition.containerDefinitions[].{Name:name,Image:image}' --output table

해결: 새 태그와 digest로 빌드해 tfvars에 반영하고 plan/apply합니다. 실제 태스크가 기대 버전인지 확인한 다음 브라우저 캐시를 점검합니다. 캐시 삭제만으로 이전 서버 이미지를 새 코드로 바꿀 수는 없습니다.

정상 확인: 예상 강의 데이터가 표시되고 배포 digest와 실제 화면이 새 버전과 일치합니다.

15. 수강신청 409와 동시 요청

증상: 신청만 실패하고 message가 표시됨. 409가 모두 인프라 장애는 아닙니다.

서버 메시지 유형 의미 사용자가 할 일
이미 신청한 강의 중복 신청 최신 내역 확인
정원 마감 다른 사용자가 먼저 신청했을 수 있음 새로고침 후 다른 강의 선택
최대 18학점 업무 제한 신청 학점 조정
시간이 겹침 수업 구간 충돌 시간표 조정
신청이 몰리고 있음 잠금·쿼리 대기 실패 내역 확인 후 잠시 뒤 재시도

원인 확인: /api/enrollments/{id}의 상태 코드와 message, 동일 시간대 DB 잠금 로그를 확인합니다. 현재 CourseService.enroll()은 학생→강의 잠금 후 중복·정원·학점·시간을 검사합니다. 여러 태스크로 늘렸다고 이 검사가 없어지지 않습니다.

해결: 원인이 업무 규칙이면 해당 조건을 해결합니다. 잠금 대기가 반복되면 장시간 트랜잭션·동일 강의 집중·DB 연결 부족을 살핍니다. 정원 검증이나 잠금을 제거해서 해결하지 않습니다.

프론트가 “요청은 완료됐지만 화면을 갱신하지 못했어요”라고 안내했다면 저장은 성공하고 refresh만 실패한 상황입니다. 같은 신청을 무조건 다시 전송하지 말고 /api/state를 재조회해 실제 내역을 확인합니다.

정상 확인: 마지막 한 자리에 동시에 요청이 와도 성공 신청 수가 정원을 넘지 않고, 취소 후 인원이 한 번만 감소해야 합니다. 운영 데이터에 부하 테스트를 바로 수행하지 말고 격리된 검증 환경을 사용합니다.

16. 배포 롤백·메모리 종료·DB 연결 부족

증상: 태스크가 반복 종료, 원하는 버전이 아닌 이전 버전으로 복귀, exit 137 또는 OOM 메시지.

원인 확인: ECS Events·stoppedReason·컨테이너 종료 사유를 먼저 읽습니다. exit 137만으로 메모리 부족을 확정할 수는 없으며 OOM 사유와 메모리 지표를 함께 확인합니다. 앱 종료 신호·강제 종료도 구분합니다.

현재 예제는 태스크당 0.5 vCPU·1 GiB, Java MaxRAMPercentage=70입니다. 힙 외에도 스레드·메타스페이스·직접 메모리 등이 필요합니다. 힙을 컨테이너 메모리 100%로 올리는 것이 해결책은 아닙니다.

해결: 실제 메모리·CPU·요청량을 측정한 뒤 적합한 Fargate CPU/메모리 조합과 JVM 설정을 조정합니다. DB pool은 기본 태스크당 10이고 롤링 배포 시 태스크 수가 늘어 총 연결 수도 증가합니다. 연결 부족을 해결하려고 모든 태스크의 pool부터 크게 늘리면 DB가 더 부담될 수 있습니다.

aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
  --query 'services[0].{TaskDefinition:taskDefinition,Deployments:deployments,Events:events[0:10]}'

이전 성공 버전으로 자동 롤백되었다면 services-stable이더라도 새 버전 배포 성공은 아닙니다. 실제 Task Definition과 digest를 비교합니다. 앱을 이전 digest로 되돌릴 때에도 이미 적용한 DB migration과 호환되는지 확인합니다. ECS 회로 차단기

정상 확인: 기대 digest가 실행 중이고 재시작이 멈추며 정상 타깃 수·메모리·DB 연결 사용량이 안정적이어야 합니다.

검증: 같은 요청 재시도 결과, 버전, health, 재발 여부
재발 방지: 테스트 / 알림 / 입력 검증 / 배포 절차 개선

가상의 학습 예: 처음 배포한 태스크가 Secret 초기화 단계에서 멈췄고 앱 로그가 없었다. Secret의 ARN은 있지만 AWSCURRENT 버전이 없음을 확인했다. 값 등록 후 새 태스크가 기동하고 health가 정상화되었다. 이 경우 결론은 “DB 비밀번호가 잘못됐다”가 아니라 “태스크에 주입할 Secret 값 버전이 준비되지 않았다”입니다. 실제 발생 기록은 아닙니다.

종료 기준은 오류 문구가 잠시 사라지는 것이 아닙니다. 의도한 버전 실행, 정상 health, 문제를 일으킨 사용자 흐름의 성공, 일정 관찰 동안 반복 실패가 없는지까지 확인합니다.

문제를 같이 진단하려면 실행한 명령·오류 문구·발생 단계·발생 시각을 전달하면 됩니다. 비밀번호·쿠키·CSRF 토큰·AWS 키는 제외합니다. 실제 로그가 없는 현재 문서는 진단 절차 안내이며 원인 확정 보고서가 아닙니다.
