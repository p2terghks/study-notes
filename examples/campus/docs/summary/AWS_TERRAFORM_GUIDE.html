수강2 프로젝트 기준 · 2026-10-08 · ECS Fargate + RDS PostgreSQL

흰색 배경과 IntelliJ IDEA 라이트 스타일 코드 색상을 사용한 새 문서입니다. 명령을 어디에서 실행하는지, 무엇이 만들어지는지, 어떤 결과를 확인해야 하는지 순서대로 설명합니다. 문서와 예제를 준비한 것이며 AWS 계정에 배포한 상태는 아닙니다.

1. 이번에 올리는 프로그램의 범위

배포 대상은 수강신청 React + Spring Boot + JPA입니다. 기존 Dockerfile이 React를 빌드한 후 결과를 Spring JAR에 넣으므로 브라우저와 API가 같은 도메인을 사용합니다. S3나 별도 React 서버 없이 이 구성을 먼저 배포할 수 있습니다.

src/main/java/ Spring API·인증·신청 업무 실행

academic-advisor/ 독립 챗봇. 현재 Docker 이미지에서 제외됨

독립 챗봇은 이번 경로에 자동으로 합쳐지지 않습니다. 별도 배포하려면 별도 이미지·ECS 서비스·라우팅과 세션 저장 방식을 준비해야 합니다. 현재 수강 서버에 남아 있는 campus/advisor Java 패키지는 JAR에 포함되지만, 별도 챗봇 React 화면과는 다릅니다.

5. 시작 전에 준비할 것

  1. AWS 계정과 권한 있는 배포용 로그인. 이 문서는 IAM Identity Center 프로필 예시를 사용합니다.
  2. 소유 도메인과 같은 계정의 실제로 권한 위임된 public Route 53 hosted zone. hosted zone을 만들기만 해서는 DNS 권한 위임이 완료되지 않습니다. 도메인 등록기관의 NS가 맞아야 합니다.
  3. AWS CLI v2, Docker Desktop/Buildx, Terraform 1.10 이상 2 미만. 예제는 AWS provider 6.x 계열을 사용합니다.
  4. 서울 리전에서 사용할 PostgreSQL 버전과 DB 인스턴스 지원 여부 확인.
  5. Terraform state용 S3 버킷 접근과 VPC·EC2 네트워크·ECS·ECR·RDS·IAM·ACM·Route 53·Logs·Secrets 리소스 생성 권한. ECS role 전달에는 iam:PassRole도 필요합니다.

infra는 VPC·서브넷·NAT·ALB·RDS·ECR 등을 만듭니다. 출력의 AdminSecretArn·AppSecretArn·DatabaseEndpoint로 앱 DB 계정을 초기화한 뒤 이미지를 올립니다. 비공개 DB 초기화 방법은 17절을 참고하세요. 기존 CloudFormation은 앱 Secret 값도 생성하지만, 새 Terraform 예제는 Secret 이름만 만들고 값을 수동 등록합니다.

export IMAGE_TAG="release-$(date -u +%Y%m%dT%H%M%SZ)"

app은 ECR 로그인 → linux/amd64 빌드·push → ECS 태스크·서비스 생성 또는 업데이트를 수행합니다. 마지막으로 도메인을 ALB에 연결하고 HTTPS를 확인합니다. 기존 스크립트는 Terraform state를 만들지 않습니다. 실제 상세 명령은 프로젝트의 deploy/README.md에 있습니다.

8. Terraform 명령과 파일의 의미

명령·파일 의미 AWS 변경 여부
terraform init backend·provider 초기화 일반적으로 인프라 생성 안 함; state 접근 가능
terraform fmt HCL 들여쓰기 정리 없음
terraform validate 설정 구조·참조·타입 검증 리소스 생성 없음
terraform plan -out=파일 원하는 구성과 현재 상태의 차이 계산 보통 조회; 변경 계획 저장
terraform apply 파일 저장한 변경 계획 실행 생성·변경·삭제 가능
terraform output 선언한 출력값 읽기 없음
.terraform.lock.hcl provider 버전·체크섬 고정 Git에 포함
terraform.tfstate 코드 주소와 실제 AWS ID의 대응 민감한 관리 데이터; Git 제외
backend.hcl state 버킷·경로·잠금 설정 비밀번호를 넣지 않음
terraform.tfvars 이 환경의 도메인·버전 등 입력 비밀정보 없이 관리

HCL의 resource는 만들 대상, data는 기존 정보 조회, variable은 외부 입력, output은 확인할 결과, locals는 중간 계산입니다. 파일 이름으로 실행 순서가 정해지지 않고 리소스 참조 관계로 순서를 계산합니다.

resource "aws_ecr_repository" "app" {
  name                 = var.name
  image_tag_mutability = "IMMUTABLE"
}

aws_ecr_repository는 리소스 종류, app은 Terraform 안의 이름입니다. var.name은 tfvars 입력입니다. 다른 리소스에서 aws_ecr_repository.app.repository_url을 참조하면 Terraform이 의존성을 인식합니다.

9. 원격 state 버킷을 먼저 준비

Terraform이 관리할 AWS 인프라보다 state 버킷을 먼저 준비합니다. 아래는 서울 리전용 AWS CLI 초기 준비 예시입니다. 이미 보안 설정된 팀 state 버킷이 있다면 재생성하지 않고 전용 key를 사용합니다.

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
STATE_BUCKET="campus-tfstate-${ACCOUNT_ID}-$(date -u +%Y%m%d%H%M%S)"

aws s3api create-bucket --bucket "$STATE_BUCKET" \
  --region "$AWS_REGION" \
  --create-bucket-configuration "LocationConstraint=$AWS_REGION"

aws s3api put-public-access-block --bucket "$STATE_BUCKET" \
  --public-access-block-configuration \
  'BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true'

aws s3api put-bucket-versioning --bucket "$STATE_BUCKET" \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption --bucket "$STATE_BUCKET" \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

버킷 이름은 전체 AWS에서 고유해야 합니다. 이름 충돌이면 새 접미사를 씁니다. state를 저장하는 버킷은 사이트 파일 공개용 버킷이 아닙니다. 이 버킷을 앱 Terraform에 포함하지 않았으므로 앱 정리 후에도 남으며 별도로 관리해야 합니다.

S3 backend는 use_lockfile = true로 동시 작업 잠금을 사용할 수 있습니다. 버전 관리는 실수로 덮어쓴 state 복구에 도움을 줍니다. backend 권한에는 버킷 ListBucket, state 객체 Get/Put, .tflock 객체 Get/Put/Delete가 필요합니다. 신규 예제는 DynamoDB 잠금 대신 S3 잠금을 사용합니다. HashiCorp S3 backend

state·저장된 plan은 민감한 자료로 취급합니다. Terraform의 sensitive 표시는 화면 노출 제한이지 state 암호화 자체가 아닙니다. 이 예제는 비밀번호 값을 Terraform에 넘기지 않지만 다른 리소스 추가 시에도 같은 보장이 자동으로 유지되는 것은 아닙니다. 민감한 데이터 관리

11. 환경값 작성

backend.hcl의 bucket을 9절에서 만든 실제 이름으로 바꿉니다. 리전도 버킷 리전과 같아야 합니다. dev/prod를 분리할 때 같은 key를 공유하지 않습니다.

bucket       = "본인이_만든_실제_버킷_이름"
key          = "campus/prod/terraform.tfstate"
region       = "ap-northeast-2"
encrypt      = true
use_lockfile = true

terraform.tfvars는 아래 입력을 채웁니다. 예제 문자열 그대로 실행하지 않습니다. domain은 내가 소유한 호스트명, zone_id는 해당 이름을 관리하는 기존 public hosted zone입니다.

region            = "ap-northeast-2"

zone_id           = "실제_PUBLIC_HOSTED_ZONE_ID"
db_engine_version = "6절에서_확인한_정확한_버전"
db_multi_az       = true
app_enabled       = false
image_uri         = ""
desired_count     = 2

처음에는 app_enabled=false입니다. 인프라를 만든 뒤 DB 계정·Secret·ECR 이미지가 준비되어야 앱을 시작할 수 있기 때문입니다. 서비스가 가동된 다음에는 false로 되돌리면 서비스와 태스크 정의의 삭제 계획이 나오므로 첫 단계 설정을 그대로 재사용하지 않습니다.

12. 네트워크 코드를 읽는 방법

network.tf는 두 가용 영역에 public·app·db 서브넷을 각각 하나씩 만듭니다. count=2와 count.index로 같은 구조를 두 번 만들고, cidrsubnet으로 /16 안에서 /24 구간을 나눕니다. 기존 VPC·VPN 주소와 겹치면 생성 전에 주소 설계를 바꿉니다.

영역 기본 외부 경로 쓰임
public 2개 Internet Gateway ALB와 NAT 배치
private app 2개 같은 AZ의 NAT Fargate, DB 초기화용 VPC 관리 환경
private db 2개 외부 기본 경로 없음 RDS

보안 그룹은 ALB의 80·443만 인터넷에 공개합니다. app의 8080은 ALB 보안 그룹만, DB의 5432는 app 보안 그룹만 허용합니다. 앱 outbound는 HTTPS 443과 DB 5432를 허용합니다. DNS는 VPC 기본 Resolver를 사용합니다.

depends_on은 값 참조만으로 드러나지 않는 실행 순서를 보충합니다. 앱 생성 전에 HTTPS Listener와 라우팅·실행 권한·보안 규칙이 준비되도록 설정했습니다. 운영에서 NAT를 VPC endpoint로 대체하려면 ECR API·ECR DKR·S3·Logs·Secrets 등의 경로를 함께 설계해야 합니다.

13. RDS·비밀번호·state 설계

data.tf의 RDS는 campus DB와 관리자 campus_admin을 만듭니다. manage_master_user_password=true로 관리자 비밀번호는 RDS가 Secrets Manager에서 관리합니다. 앱에는 관리자 계정을 주지 않고 이후에 만들 campus_app을 사용합니다. aws_db_instance 공식 스키마

앱 Secret 리소스는 이름과 ARN만 생성합니다. secret_string, random_password의 결과, 비밀번호를 읽는 data source를 이 예제에 넣지 않았습니다. 실제 앱 비밀번호는 16절에서 콘솔에 저장하고 DB 계정에도 같은 값을 설정합니다. 이름만 존재하고 값 버전이 없는 Secret을 ECS에 전달하면 태스크 시작이 실패합니다.

deletion_protection=true는 AWS의 DB 삭제 방지이고 prevent_destroy=true는 Terraform의 삭제 계획 방지입니다. 서로 다른 장치입니다. skip_final_snapshot=false는 삭제 시 마지막 스냅샷을 요구합니다. 스냅샷 이름이 이미 존재하면 삭제 시 새 고유 이름을 지정해야 합니다.

예제의 자동 백업은 7일, 암호화는 활성화, Multi-AZ는 기본 true입니다. Multi-AZ는 장애 대응용이며 읽기 부하를 분산하는 read replica와 다릅니다. 앱 데이터·로컬 H2 파일을 이 리소스가 자동으로 이관하지는 않습니다.

14. 도메인과 HTTPS는 어떻게 만들어지나

web.tf는 ACM 인증서 신청 → DNS 검증 CNAME 생성 → 검증 완료 대기 → ALB HTTPS Listener 생성 순으로 연결됩니다. Route 53 A Alias는 사용자 도메인을 ALB에 연결합니다. ACM 검증 CNAME은 이후 인증서 갱신에 필요하므로 남겨둡니다. ACM DNS 검증

ALB와 인증서는 같은 AWS provider 리전에서 생성됩니다. 이 앱은 CloudFront 경로가 아니므로 인증서를 무조건 버지니아 리전에 만들지 않습니다. 접속은 ALB의 긴 기본 DNS 이름이 아니라 인증서에 등록한 사용자 도메인으로 합니다.

80번 Listener는 HTTPS로 리다이렉트하고 443번 Listener가 타깃 그룹의 8080으로 전달합니다. target_type="ip"는 awsvpc로 실행하는 Fargate의 태스크 IP를 대상으로 하기 때문입니다. readiness 경로는 실제 프로젝트에서 공개되고 DB 상태도 포함하는 /actuator/health/readiness입니다.

외부 DNS 업체를 계속 사용한다면 현재 예제의 Route 53 레코드 리소스를 그대로 사용할 수 없습니다. 인증서 검증 레코드와 서비스 레코드를 외부 업체에 생성하는 흐름으로 수정해야 합니다. 이 예제는 Route 53에서 권한 있는 public zone을 이미 보유한 경우를 전제로 합니다.

15. 1차 적용 — 인프라만 생성

실행 위치: infra/terraform/. AWS 프로필·리전 환경변수가 같은 터미널에 설정되어 있어야 합니다.

terraform init -backend-config=backend.hcl
terraform fmt -check
terraform validate
terraform plan -out=infra.tfplan

plan의 +는 생성, ~는 변경, -는 삭제, -/+는 교체입니다. 최초 새 환경에서는 생성 계획이 중심이어야 합니다. 예상하지 않은 기존 DB 삭제·교체가 보이면 apply하지 않고 계정·state key·리소스 이름부터 확인합니다. plan이 계정 권한·DNS·리전 가용성까지 모두 보증하지는 않습니다.

# 계획을 검토한 뒤 실행
terraform apply infra.tfplan
terraform output

RDS 생성과 ACM 검증은 시간이 걸릴 수 있습니다. DNS 검증 대기가 길면 NS 위임과 CNAME을 확인합니다. 아직 앱을 만들지 않았으므로 ALB가 503을 내는 것은 이 단계에서는 예상되는 상태입니다.

출력 확인 항목: repository_url, database_endpoint, admin_secret_arn, app_secret_arn, vpc_id, app_subnet_ids, app_security_group_id, log_group, site_url. 아직 service_name은 출력되지 않거나 null인 상태입니다.

AWS 콘솔 → Secrets Manager → 출력된 app_secret_arn에 해당하는 Secret → 비밀 값 편집 화면에서 아래 두 키를 저장합니다. 콘솔 명칭은 화면 버전에 따라 조금 다를 수 있습니다.

{
  "username": "campus_app",
  "password": "새로_생성한_충분히_긴_실제_비밀번호"

태스크 정의의 :username::와 :password::는 Secret JSON 안의 해당 키를 읽습니다. Linux Fargate의 JSON 키 선택 주입에는 플랫폼 1.4.0 이상이 필요하므로 예제는 1.4.0을 지정했습니다. Secret을 바꾸어도 이미 실행 중인 컨테이너 환경변수는 즉시 바뀌지 않아 새 태스크 배포가 필요합니다. ECS Secret 환경변수

17. 비공개 RDS에 앱 계정을 생성

실행 위치: VPC에 접근 가능한 관리 환경. 개인 노트북이나 기본 CloudShell은 private RDS에 바로 접속할 수 없습니다.

CloudShell의 VPC 환경을 만들 때 이 Terraform 출력의 VPC, app subnet 중 하나, app security group을 선택합니다. app subnet의 NAT로 HTTPS 다운로드가 가능하고 보안 그룹으로 RDS 5432 접속이 가능합니다. 해당 리전·계정에서 VPC CloudShell을 사용할 수 없는 경우 SSM으로 접속 가능한 관리 호스트 등 대체 경로가 필요합니다. CloudShell VPC 환경

먼저 psql --version으로 클라이언트를 확인합니다. 없으면 관리 환경의 OS에 맞는 PostgreSQL 클라이언트를 준비합니다. 로컬 파일이 VPC 환경에 자동으로 복사되지는 않으므로 deploy/bootstrap-db.sql의 내용을 관리 환경에 가져옵니다.

curl --fail --location \
  https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem \
  -o global-bundle.pem

# 실제 database_endpoint를 넣고 실행. 관리자 비밀번호는 -W 프롬프트에 입력
psql "host=실제_RDS_ENDPOINT port=5432 dbname=campus user=campus_admin sslmode=verify-full sslrootcert=global-bundle.pem" -W

관리자 비밀번호는 Secrets Manager의 admin_secret_arn에서 확인합니다. 관리자용과 앱용 Secret을 혼동하지 않습니다. verify-full은 암호화뿐 아니라 CA와 호스트명을 검증합니다. 인증 오류를 무작정 sslmode=disable로 해결하지 않습니다. RDS PostgreSQL TLS

-- psql 안에서 최초 한 번 실행: 기존 deploy/bootstrap-db.sql과 같은 내용
CREATE ROLE campus_app LOGIN;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
GRANT CONNECT ON DATABASE campus TO campus_app;
GRANT USAGE, CREATE ON SCHEMA public TO campus_app;

-- SQL 문자열에 비밀번호를 적지 않고 psql 프롬프트 사용
\password campus_app

여기에는 16절 앱 Secret의 password와 동일한 값을 입력합니다. 이미 계정이 있다면 CREATE ROLE을 다시 실행하는 대신 역할·권한·소유권을 확인합니다. 새 빈 DB를 기준으로 한 절차이며 기존 테이블 소유권 변경이나 데이터 이관까지 자동으로 해주지는 않습니다.

-- 세션 종료
\q

같은 psql 접속 문자열에서 user를 campus_app으로 바꾸어 재접속하고 SELECT current_user, current_database();로 확인합니다. 실제 앱 계정으로 접속이 되어야 다음 단계로 갑니다. 초기화용 VPC 환경을 정리한 뒤에도 ECS가 쓰는 app 보안 그룹 자체는 삭제하지 않습니다.

18. React·Spring 이미지를 ECR에 올리기

실행 위치: 개발 PC의 수강2 루트. 아래 TF_DIR는 10절에서 복사한 폴더 기준입니다.

TF_DIR=infra/terraform
REPOSITORY_URL=$(terraform -chdir="$TF_DIR" output -raw repository_url)
REPOSITORY_NAME=$(terraform -chdir="$TF_DIR" output -raw repository_name)
REGISTRY="${REPOSITORY_URL%%/*}"
IMAGE_TAG="release-$(date -u +%Y%m%dT%H%M%SZ)"

aws ecr get-login-password --region "$AWS_REGION" \
  | docker login --username AWS --password-stdin "$REGISTRY"

docker buildx build --platform linux/amd64 --provenance=false \
  --tag "$REPOSITORY_URL:$IMAGE_TAG" --push .

IMAGE_DIGEST=$(aws ecr describe-images --region "$AWS_REGION" \
  --repository-name "$REPOSITORY_NAME" \
  --image-ids "imageTag=$IMAGE_TAG" \
  --query 'imageDetails[0].imageDigest' --output text)
IMAGE_URI="$REPOSITORY_URL@$IMAGE_DIGEST"
printf '%s\n' "$IMAGE_URI"

마지막 .은 현재 디렉터리를 Docker 빌드 입력으로 사용한다는 뜻입니다. infra/terraform 안에서 실행하면 루트 Dockerfile을 찾지 못하므로 프로젝트 루트로 돌아옵니다. Apple Silicon Mac에서도 명시한 linux/amd64가 ECS의 X86_64와 일치해야 합니다.

ECR 태그는 IMMUTABLE이라 같은 태그로 덮어쓰기하지 않습니다. 매번 새 IMAGE_TAG를 사용하고 실제 배포는 @sha256:... digest로 고정합니다. digest가 None이면 업로드와 태그를 확인하고 진행하지 않습니다. ECR 이미지 업로드

Dockerfile은 React 테스트·빌드 → Maven verify → JRE 실행 이미지 순으로 묶습니다. Node 개발 서버는 운영에서 실행되지 않습니다. 독립 academic-advisor 디렉터리는 .dockerignore로 제외됩니다. PostgreSQL 전용 테스트는 별도 임시 DB 검증이며 이미지 빌드 성공만으로 실제 RDS 접속을 확인한 것은 아닙니다.

19. 2차 적용 — 앱 태스크와 서비스 시작

infra/terraform/terraform.tfvars에서 두 값을 수정하여 파일에 유지합니다. CLI의 임시 -var만 쓰고 파일을 false로 남겨두면 다음 plan이 앱을 제거할 수 있습니다.

app_enabled = true
image_uri   = "123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/campus-tf@sha256:실제_DIGEST"

위 URI는 형식 예시입니다. 18절에서 출력한 실제 IMAGE_URI 전체를 그대로 넣습니다. Secret 값 등록과 DB 앱 계정 확인을 마친 상태여야 합니다.

cd infra/terraform
terraform plan -out=app.tfplan
terraform apply app.tfplan

plan에는 Task Definition과 ECS Service 생성이 나타나야 합니다. ecs.tf는 컨테이너 8080, CPU 512(0.5 vCPU), 메모리 1024 MiB, 태스크 기본 2개, private subnet, public IP 없음으로 정의합니다. 태스크에 prod·DB_URL·DB_POOL_SIZE와 Secret의 username/password가 주입됩니다.

Execution Role은 ECS 에이전트가 ECR 이미지·로그·Secret을 다루기 위한 권한입니다. Task Role은 컨테이너 앱 코드가 AWS SDK를 사용할 때의 권한입니다. 현재 앱은 DB에 JDBC로 연결하므로 Task Role에 광범위한 AWS 권한을 줄 이유가 없습니다. 사용자 관리 KMS 키로 Secret을 바꾼다면 Execution Role의 해당 키 복호화 권한도 검토해야 합니다. ECS Execution Role

예제는 wait_for_steady_state를 사용하지만 Terraform 종료 코드만으로 최종 버전을 단정하지 않습니다. 회로 차단기가 이전 버전으로 복구했을 수도 있으므로 다음 절에서 서비스 이벤트·실제 Task Definition·이미지 digest를 확인합니다.

20. 첫 시작에서 일어나는 일

태스크 생성
→ Execution Role로 ECR pull / Secret 읽기 / 로그 스트림 준비
→ Spring prod 시작
→ RDS TLS 접속
→ Flyway: V1 업무 테이블 → V2 공유 세션 → V3 상담 프로필
→ JPA ddl-auto=validate로 매핑 검증
→ readiness UP
→ ALB가 정상 대상으로 등록
→ HTTPS 사용자 요청 전달

현재 소스에는 V1·V2·V3가 있습니다. 다음 DB 변경은 기존 파일을 수정하지 않고 새 V4 이상으로 추가합니다. 여러 태스크가 동시에 부팅하면 Flyway가 마이그레이션 실행을 조정합니다.

운영에서는 데모 강의·체험 계정 자동 생성이 꺼져 있습니다. 최초 DB가 비어 있으면 회원가입은 가능하지만 강의 목록은 비어 있습니다. 실제 강의와 수업 시간을 승인된 입력·마이그레이션 절차로 준비해야 하며 현재 관리자 강의 관리 화면은 없습니다. 로컬 H2 데이터를 RDS에 자동 복사하지 않습니다.

21. 배포가 잘 되었는지 확인

실행 위치: 개발 PC, 수강2 루트. 다음은 읽기용 상태 확인입니다.

수동 앱 롤백은 ECR에 남아 있는 이전 정상 digest를 tfvars에 다시 넣고 plan/apply합니다. ECR 정리 정책을 추가할 때 롤백 후보 이미지를 함께 지우지 않도록 보존 규칙을 설계합니다. 이 예제는 ECR 이미지를 자동 삭제하지 않습니다.

앱 롤백은 DB 스키마 롤백과 다릅니다. 새 Flyway 버전이 적용된 뒤 이전 코드가 실행되어도 되는지 검토해야 합니다. 먼저 새 컬럼을 추가하고 양쪽 코드가 읽을 수 있게 한 뒤, 나중에 불필요한 컬럼을 제거하는 식으로 단계적으로 바꿉니다. DB 복구가 필요하면 백업/PITR에서 새 인스턴스로 복구하는 계획과 데이터 손실 범위를 따로 다룹니다.

25. 기존 CloudFormation 환경을 Terraform으로 옮길 때

이 문서의 기본 경로는 새 환경 생성입니다. 이미 실제 서비스가 있다면 terraform apply로 똑같은 이름의 리소스를 다시 만드는 것이 이관이 아닙니다. Terraform import는 기존 AWS 리소스를 state의 주소에 연결하는 과정입니다. Terraform import

  1. 실제 CloudFormation 스택·리소스 ID·데이터 백업·현재 구성부터 기록합니다.
  2. 각 리소스와 관계를 HCL로 정확히 작성합니다. 새 예제의 주소를 기존 ID에 무조건 끼워 맞추지 않습니다.
  3. 해당 리소스의 CloudFormation 삭제·교체 시 Retain 정책을 준비하고 변경 계획을 검토합니다.
  4. 유지한 실제 리소스를 기존 스택 관리에서 분리하는 절차를 수행합니다. 스택 전체를 무심코 삭제하지 않습니다.
  5. Terraform import 후 plan이 의도하지 않은 변경 없이 맞는지 확인합니다.
  6. 그 다음 변경부터 Terraform만 소유권을 가지고 관리합니다.
# 개념 예시. 실제 ID와 resource 정의를 함께 맞춰야 한다.
import {
  to = aws_ecr_repository.app
  id = "실제_기존_ECR_저장소_이름"
}

import는 데이터를 새로 복사하거나 AWS 리소스를 재생성하는 기능이 아닙니다. 서비스 중단 없는 이관은 리소스별 별도 계획이 필요합니다. 새 환경을 사용한다면 기존 사용자 데이터 이관, 도메인 전환, TTL, 세션 만료와 롤백 기준도 따로 정합니다.

26. 운영과 비용 정리

CloudWatch에서 앱 오류·태스크 재시작·ALB 5xx·DB 연결 수와 저장량을 확인합니다. 예제에는 자동 스케일링, WAF, 운영 알람, ALB 액세스 로그 저장, CI/CD 파이프라인이 포함되어 있지 않습니다. 현재 부하를 측정한 후 단계적으로 추가합니다.

리소스 정리도 plan으로 먼저 확인합니다. 아래는 삭제 실행 명령이 아닌 검토용 명령입니다.

terraform plan -destroy

현재 prevent_destroy 때문에 일부 삭제 계획은 차단됩니다. 실제 삭제가 필요하면 보존 대상·백업·최종 스냅샷 이름을 확정하고, RDS·ALB의 삭제 방지와 Terraform lifecycle 보호를 각각 이해한 상태에서 변경합니다. Terraform 설정 블록 자체를 제거하면 prevent_destroy만으로 보호되지 않는 경우도 있으므로 이 값을 백업으로 생각하면 안 됩니다.

ECR force_delete=false는 이미지가 남은 저장소 삭제를 거부합니다. Secret은 30일 복구 유예를 사용합니다. RDS 스냅샷, state S3 버킷·버전, ECR 이미지, 남아 있는 NAT/EIP·CloudWatch 리소스의 비용도 별도로 확인합니다. 이 가이드 작성 중에는 어떤 destroy/apply도 AWS에 실행하지 않았습니다.

27. 한 번에 기억하는 실행 순서

AWS 로그인·계정 확인
→ 도메인 public zone 위임 확인
→ state S3 버킷 준비
→ 예제 복사 / backend.hcl·tfvars 작성
→ init → fmt → validate → infra plan → apply
→ 앱 Secret 값 등록
→ VPC 관리 환경에서 campus_app 생성·비밀번호 설정
→ 개발 PC에서 Docker 이미지 빌드·ECR push
→ digest를 tfvars에 기록 / app_enabled=true
→ app plan → apply
→ ECS 실제 버전·ALB·HTTPS·DB·로그인·신청 확인
→ 다음 배포는 새 이미지 digest로 반복

설명 중 실행하지 않은 계정별 항목: DNS 권한 위임, 계정 IAM 정책, 리전별 인스턴스/엔진 가용성, 실제 RDS TLS 연결, 도메인 HTTPS, 서비스 부하. 로컬 코드 검증 결과와 AWS 실제 배포 검증 결과를 구분합니다.

29. 검증 범위와 공식 참고 자료

검증 완료: Terraform 1.14.0 + AWS provider 6.68.0에서 init -backend=false, validate, fmt -check가 통과했습니다. backend=false로 state 버킷에 연결하지 않았고 AWS plan/apply는 실행하지 않았습니다. 예제 파일과 HTML 코드의 일치, 문서 목차·모바일 배치는 별도로 확인했습니다. 실제 계정 배포 성공을 보증하는 결과는 아닙니다.

Terraform 예제 전체를 ZIP 파일로 받기. 소스 코드를 공부하려면 기존 전체 코드 설명을 참고하세요.

공식 문서는 설명 중 해당 단계에 연결했습니다. 핵심 확인 항목은 S3 backend 잠금, ECS Secret 주입, RDS TLS, ECS 롤백, Terraform import입니다.
